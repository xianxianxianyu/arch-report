# Agent 服务器架构雷达｜2026-07-23 11:59 +08:00

本轮从 10 个新审阅候选与 1 个未发布合格库存中选出 5 篇。最高推荐是 **Murakkab**：不要把 Agent 工作流作为不可见的模型/工具调用串交给通用扩缩容器；应把工作流结构、候选执行配置和请求 SLO 分离，让运行时按已验证的配置画像做准入、映射和重配置。

## 本轮覆盖

| 生产问题 | 入选机制 | 采用方向 |
|---|---|---|
| 工作流配置与模型/硬件绑定，负载变化后成本上升或 SLO 失守 | 声明式工作流、离线画像、SLO 过滤、运行时重配置 | 将 Agent 图编译为可版本化 IR，按请求类别选择执行计划 |
| 每步同步持久化令长链路延迟随 DAG 深度累积 | 依赖图、可恢复边界、协调回滚、隔离恢复世代 | 先在非外部可见阶段投机执行，提交边界后再暴露结果 |
| 不可信代码能读取宿主凭证、联网外传或污染文件系统 | 凭证隔离、默认禁网、只读根文件系统与临时写层 | 工具执行面与控制面分进程，网络和产物导出显式授权 |
| 多租户共享 IP 时无法证明请求来自哪个 Agent | RFC 9421 HTTP 消息签名、密钥目录、边缘验证标签 | 出站请求签名，入口按 verified/invalid/expired/unknown 决策 |
| 语义相似但业务边界错误的记忆混入上下文 | 租户 namespace、确定性元数据、检索前过滤 | “租户隔离键”与“检索相关键”分层，禁止只靠向量相似度 |

## 1. Murakkab：让 SLO 成为 Agent 工作流运行时的输入

**评分：98/100**（来源 25、问题 20、架构 25、证据 14、服务端价值 14）  
**原始来源：** [OSDI 2026 正式论文页](https://www.usenix.org/conference/osdi26/presentation/chaudhry) · [论文 PDF](https://www.usenix.org/system/files/osdi26-chaudhry.pdf)

### 针对的问题

**来源事实/作者主张：** 现有 Agent 框架把工作流逻辑、模型选择、参数和 CPU/GPU 配置写在同一个命令式 DAG 中；配置空间随工作流、Agent 与硬件旋钮组合增长，负载或资源变化后必须人工改写和重部署。作者报告，静态框架不能区分高准确率与低延迟请求，造成资源浪费和 SLO 违约。

**本项目工程推断：** 服务端若只对“整个 Agent Pod”扩缩容，就看不到阶段级瓶颈，也无法在质量、延迟和成本间做请求级选择。

### 原设计

Murakkab 用声明式规格分离工作流结构、任务依赖和低层执行配置；离线画像形成模型、硬件、并行度与工作流旋钮的候选集合，优化器先按准确率、TTFT/TPOT、成本等 SLO 过滤，再由自适应运行时映射组件并随负载重配置。论文在多种工作流上报告 GPU 用量最多降低 2.8 倍、能耗 3.7 倍、成本 4.3 倍，同时保持 SLO；这些是作者实验结果，不是本项目复测结论。

### 对 Agent 服务器的采用设计

把每个 Agent 版本编译为不可变 `workflow_ir`，节点只声明输入输出、候选实现、资源画像和副作用等级；控制面维护 `execution_profile` 与 `plan_version`，入口按 `latency/quality/cost` 请求类别选择已验证计划。运行中只允许在同一兼容性集合内重配置；涉及副作用的工具节点不得因成本优化而自动换实现。

### 验收不变量

故障注入：在 30 分钟内将某模型队列延迟提高 3 倍并制造 GPU 紧张。必须满足：所有已接受请求的 SLO 违约率不高于静态基线；任何计划切换都能由 `request_id + workflow_version + plan_version` 重放；副作用工具的实现和幂等键不因重配置改变。

### 边界与风险

论文评估不等于真实业务质量；画像会老化，错误画像可能把流量推向不可行配置。最小实现应先做 SLO 分类、计划版本和影子评估，不应一开始建设全局求解器。

## 2. libDSE：持久执行可以投机，但外部可见性不能投机

**评分：98/100**（来源 25、问题 20、架构 25、证据 15、服务端价值 13）  
**原始来源：** [OSDI 2026 正式论文页](https://www.usenix.org/conference/osdi26/presentation/li-tianyu) · [论文 PDF](https://www.usenix.org/system/files/osdi26-li-tianyu.pdf)

### 针对的问题

**来源事实/作者主张：** 常见 durable execution 在每个任务输出后同步持久化，延迟开销随任务图深度累积；若直接省略持久化，非确定性重放会产生分叉任务和冲突副作用。

**本项目工程推断：** 长 Agent 链最危险的不是重复计算，而是把尚不可恢复的中间决定发给用户、支付系统或外部工具。

### 原设计

libDSE 把状态操作组织成原子 action，以消息头记录因果依赖；协调器维护依赖图，只有落在“可恢复闭包”中的结果才能对外暴露。故障时用单调递增的 failure sequence 协调各参与者回滚，并禁止恢复前后两个世代相互消费消息。论文给出的核心保证是最终修复不一致，以及外部实体永远看不到故障诱发的不一致；作者报告持久化受限应用端到端延迟最多降低一个数量级。

### 对 Agent 服务器的采用设计

不直接复刻 libDSE，而采用其边界：推理、纯读取和可丢弃中间产物可在 `speculation_epoch` 内并行；工具写操作、用户最终答复和事件发布必须等待依赖闭包提交。每条内部消息携带 `run_id/action_id/state_version/failure_epoch`；恢复后拒绝旧 epoch 消息。

### 验收不变量

故障注入：在“工具返回成功、状态尚未持久化”窗口杀死 orchestrator，并制造重复恢复。必须满足：外部系统最多观察到一个相同幂等键的提交；旧 failure epoch 的消息不进入新状态；最终公开答复引用的每个 action 均位于已提交依赖闭包。

### 边界与风险

论文假设 fail-restart、可靠点对点通信且不处理拜占庭故障；回滚协议和依赖图本身有显著复杂度。第一阶段只应对纯计算分支投机，外部副作用仍使用同步 outbox/幂等提交。

## 3. Cloud Run sandboxes：工具执行默认拿不到凭证、网络和持久写权限

**评分：95/100**（来源 24、问题 20、架构 23、证据 13、服务端价值 15）  
**原始来源：** [Google Cloud 官方工程博客](https://cloud.google.com/blog/topics/developers-practitioners/google-cloud-run-sandboxes-are-in-public-preview/)

### 针对的问题

**来源事实/作者主张：** AI 生成代码或不可信二进制若与宿主服务同权限运行，可能读取环境变量和云元数据凭证、通过网络外传数据，并污染共享文件系统。

**本项目工程推断：** “容器里再起子进程”不是 Agent 工具隔离；执行单元必须默认没有控制面的身份和出站能力。

### 原设计

Cloud Run 在现有服务实例内启动轻量隔离边界。沙箱看不到服务环境变量和元数据服务器，网络出站默认拒绝，容器文件系统只读，写入进入执行结束即丢弃的内存 overlay；导入、导出文件和开放出站均需显式参数。官方示例启动并销毁 1,000 个沙箱的平均延迟为 500ms，这是供应商演示数据。

### 对 Agent 服务器的采用设计

tool gateway 只向沙箱传递任务级 capability 和输入 artifact，不挂载租户长期凭证。网络按目标域、方法和时间窗签发一次性 egress grant；产物只通过扫描后的 export 通道进入 artifact store，并绑定 `tenant_id/run_id/tool_call_id`。

### 验收不变量

故障注入脚本同时尝试读取环境变量、访问云元数据、连接未授权域名和修改根文件系统。四项必须全部失败；只有列入授权的导出文件可在沙箱结束后存在，且产物哈希与审计事件一致。

### 边界与风险

该能力仍是 public preview；博客未给出隔离实现的独立安全评估。共享宿主资源也意味着需另做 CPU、内存、进程数和 fork-bomb 限额。

## 4. Web Bot Authentication：共享出口 IP 不能充当 Agent 身份

**评分：94/100**（来源 24、问题 20、架构 23、证据 13、服务端价值 14）  
**原始来源：** [AWS Security 官方技术博客](https://aws.amazon.com/blogs/security/authenticate-legitimate-ai-agent-traffic-with-aws-waf-bot-control/)

### 针对的问题

**来源事实/作者主张：** 多租户运行时中成千上万个 Agent 共享 IP，IP 白名单和反向 DNS 无法区分调用者，User-Agent 又可伪造，导致合法 Agent 被拦截或攻击者被误放行。

**本项目工程推断：** tool gateway 的出站身份必须绑定请求内容、密钥和时效，不能继承宿主网络位置的信任。

### 原设计

Agent 运营者在目录发布公钥，并依据 RFC 9421 对 HTTP 消息签名；边缘验证 Ed25519 签名后写入 `verified`、`invalid`、`expired` 或 `unknown_bot` 标签，再由策略决定放行、限速、告警或阻断。签名输入含 authority、key id、created、expires、nonce 等；AWS 同时提供账户级标签和监控指标。

### 对 Agent 服务器的采用设计

在统一 egress proxy 内完成签名，私钥不进入 Agent 沙箱。密钥按租户与调用角色轮换；策略同时校验签名、目标 audience、工具 capability 和用户委托链。接收侧保留验证标签、key id、nonce 与决策原因。

### 验收不变量

故障注入：重放已签名请求、篡改 authority、使用过期密钥、从另一租户复用签名。四种请求均不得获得 `verified`；同一 nonce 在有效窗内只接受一次；未知身份只能进入显式隔离策略，不能继承默认放行。

### 边界与风险

WBA 证明请求由某密钥持有者发出，不证明 Agent 行为被用户授权，也不替代 OAuth/OBO。文中的独立注册 API 仍在 roadmap，标准与供应商支持可能变化。

## 5. Structured memory filtering with metadata in AgentCore Memory：先确定边界，再做相似度

**评分：92/100**（来源 24、问题 19、架构 21、证据 14、服务端价值 14）  
**原始来源：** [AWS 官方技术博客](https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/)

### 针对的问题

**来源事实/作者主张：** 单靠 namespace 只能隔离“谁”，在同一客户数月历史中，语义相似的不同部门、时间或优先级记录仍会混入结果。作者在 151 问题测试集上报告总体 QA 准确率由 40% 升至 64%，依赖上下文边界的问题由 16% 升至 69%。

**本项目工程推断：** 记忆污染既是质量问题，也是越权问题；租户边界不能交给 embedding 或 LLM 推断。

### 原设计

设计分三阶段：配置时声明可索引 schema；摄取时把确定性字段原样传播，把允许推断的字段交给 LLM；检索时先执行 namespace 与元数据过滤，再做 KNN。`STRICTLY_CONSISTENT` 字段还参与抽取和合并分区，值不同的记录不会因语义相似而合并。

### 对 Agent 服务器的采用设计

将 `tenant_id/principal_id/data_classification` 设为应用写入且不可由模型推断的安全键；`topic/sentiment` 才允许模型推断。查询由策略层注入安全过滤器，Agent 只能追加业务相关过滤条件，不能删除或放宽安全条件。记录保留来源 Agent、workflow step 和写入事件 ID。

### 验收不变量

故障注入：写入内容高度相似但租户、部门或密级不同的记录，并诱导 Agent 请求“忽略过滤”。返回集必须 100% 满足服务端注入的安全谓词；不同确定性键的记录不得合并；每条召回结果可追溯到原始事件。

### 边界与风险

评估由供应商报告且未独立复现；最多三个 `STRICTLY_CONSISTENT` 键、十个索引槽且索引键不可删除，会把早期 schema 决策变成迁移成本。元数据过滤也不能替代存储层访问控制。
