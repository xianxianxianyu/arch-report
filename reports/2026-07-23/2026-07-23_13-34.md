# Agent 服务器架构雷达｜2026-07-23 13:34 +08:00

本轮复核 2 个未发布合格库存，并深读 5 个新候选；最终选出 5 篇，覆盖 5 类生产问题。最高推荐是 **Cloudflare Agents SDK v0.17.0 的后台运行模型**：后台子 Agent 不应是“从请求里启动的异步函数”，而应是有稳定身份、统一准入、持久进度、预算上限和故障后协调修复的运行实体。这样部署、驱逐、断线与父任务结束才不会把工作静默丢失。

## 本轮覆盖

| 生产问题 | 入选机制 | 采用方向 |
|---|---|---|
| 父任务结束、部署或驱逐后，后台子 Agent 被遗弃或重复执行 | 持久 run、reconcile、统一 `runTurn` 准入、预算与终态 | 将每个后台任务注册为可恢复运行实体，而非进程内 Promise |
| Agent 在终端本地执行会绕过企业身份、网络、凭证与审计边界 | 受管工作区、默认拒绝网络、凭证代理、签名策略 | 端点只做展示；执行、工具访问和审计进入受控工作区 |
| 等待工具或数据的任务持续占用计算，进程快照又过重 | continuation capture、I/O effect、可迁移恢复 | 在工具边界保存逻辑 continuation，并把副作用交给受控适配器 |
| 偶发推理慢 token 破坏 SLO，但全量 tracing 开销过高 | 关键同步点、关键路径、异常时细化、动态 roofline | 常开低成本骨架 trace，异常请求再升级采样与诊断 |
| MCP、Memory、Gateway、Guardrail 全部串在主链路后，单点超时拖垮请求 | 并行初始化、超时降级、异步保存、令牌提前刷新 | 为每个依赖定义超时、降级、刷新和审计契约 |

## 1. Agents SDK v0.17.0：后台子 Agent 必须是持久运行实体

**评分：98/100**（来源 24、问题 20、架构 25、证据 14、服务端价值 15）  
**原始来源：** [Cloudflare 官方 Changelog](https://developers.cloudflare.com/changelog/post/2026-06-26-agents-sdk-v0.17.0/) · [官方代码仓库](https://github.com/cloudflare/agents)

### 针对的问题

**来源事实/作者主张：** 从父 turn 直接派生的后台子 Agent 会在父 turn 结束、Durable Object 驱逐或部署后被遗弃；多个 `wait/submit/stream` 入口如果各自准入，嵌套阻塞调用可能死锁；挂起的模型流和重连竞态还可能让客户端永久停在 busy 状态。

**本项目工程推断：** 只要工作可能跨越一次 HTTP/WebSocket 生命周期，运行身份和进度就必须先于执行持久化；“fire-and-forget”只能描述调用方体验，不能描述服务端生命周期。

### 原设计

Cloudflare 让 `runAgentTool` 返回 detached run handle，由可跨驱逐和部署的自调度 reconcile backbone 持有运行；完成状态显式为 `completed/error/aborted/interrupted`。`maxBudgetMs` 与取消接口限制孤儿任务占用并发槽；最新 progress 持久化，命名 milestone 进入可重放记录。`runTurn` 再把 `wait/submit/stream` 汇入同一准入路径，并在嵌套阻塞准入时直接报错。恢复侧加入 stalled-stream watchdog、被中断工具调用修复和子 Agent 重新挂接。官方只声称“happy path 上 exactly-once”，不能外推为端到端严格一次。

### 对 Agent 服务器的采用设计

新增 `agent_run` 注册表：`run_id/root_run_id/parent_run_id/tenant_id/input_hash/budget_deadline/lease_epoch/state/latest_milestone`。入口先以幂等键创建或取得 run，再由统一 admission service 发放带 fencing token 的执行租约；worker 只写入当前 epoch。进度走可覆盖快照，里程碑与终态走追加日志；完成通知通过 outbox 投递，消费者按 `run_id + terminal_version` 去重。同步、提交、流式只是等待策略不同，不得绕过同一准入状态机。

### 验收不变量

故障注入：分别在子 Agent 运行中杀死父 worker、替换部署版本、断开客户端并让模型流卡死。必须满足：同一 `run_id` 最终只有一个终态；旧 lease epoch 不能继续提交；完成副作用按幂等键最多一次；进度在重连后可恢复；超过 budget 的任务最终释放并发槽；嵌套阻塞准入在执行任何工具前被拒绝。

### 边界与风险

这是官方产品发布说明而非独立评测；协调器、持久日志和 outbox 本身会增加写放大与恢复复杂度。实验性的 server actions/channels 不应成为首版依赖；最小落地只实现 run 注册、租约、里程碑、终态和协调扫描。

## 2. Secure Agent Workspace：端点只展示，Agent 在受管边界内执行

**评分：97/100**（来源 24、问题 20、架构 24、证据 14、服务端价值 15）  
**原始来源：** [NVIDIA 官方技术博客](https://developer.nvidia.com/blog/how-to-govern-autonomous-agents-in-enterprise-ai-factories) · [企业参考架构](https://docs.nvidia.com/enterprise-reference-architectures/secure-agent-workspace-reference-design/latest/index.html) · [OpenShell 官方仓库](https://github.com/NVIDIA/OpenShell)

### 针对的问题

**来源事实/作者主张：** 长时间运行的 Agent 会读取文件、执行命令、调用企业系统；若在用户端点或普通共享环境内执行，就难以统一执行 SSO、网络默认拒绝、短期凭证、人审门和中心审计，Agent 还可能静默扩大自身权限。

**本项目工程推断：** “用户登录过的电脑”不是可继承的 Agent 信任域。端点身份只能用于建立会话，不能直接变成沙箱内的长期密钥或无限制网络能力。

### 原设计

NVIDIA 将笔记本、浏览器、IDE 和终端定义为 presentation layer；实际执行进入每用户受管 VM。外层由 trusted access broker、SSO、默认拒绝出站、中心日志和工作区生命周期控制；内层由 runtime sandbox、签名策略、credential proxy、推理网关与工具前审批控制。策略和 VM 模板用 GitOps 管理，原始凭证尽量留在代理后方，审计输出到 SIEM/OCSF 路径。OpenShell 仓库给出容器、网关、策略引擎和推理路由实现，但明确标注为 alpha、single-player。

### 对 Agent 服务器的采用设计

把 `workspace_id` 作为运行、身份和审计的共同边界。控制面依据用户委托创建短期工作区和 capability manifest；数据面只接收签名策略、任务级令牌和允许的 artifact。所有模型与工具调用经 egress/credential proxy，沙箱从不读取上游原始密钥。高影响工具动作先写 `pending_action`，由工作区外的审批服务决定；端点断线不改变执行权限，也不使权限续期。

### 验收不变量

故障注入：在工作区内尝试读取长期密钥、访问未授权域、修改策略文件、绕过代理直连工具，并伪造过期策略版本。五项必须全部失败且生成审计事件；每次外部工具调用都能关联 `tenant_id/user_delegation/workspace_id/run_id/policy_version`；撤销工作区后，旧会话和旧 capability 均不得恢复访问。

### 边界与风险

参考架构带有供应商立场，未给出独立生产评估；每用户 VM 的隔离强但容量和运维成本高。OpenShell 当前不是成熟多租户控制面，因此可采用架构不变量，但不能把仓库现状当作企业级隔离已经完成。

## 3. Arca：在等待边界保存“余下程序”，而不是冻结整个进程

**评分：97/100**（来源 25、问题 20、架构 25、证据 15、服务端价值 12）  
**原始来源：** [OSDI 2026 正式论文页](https://www.usenix.org/conference/osdi26/presentation/srivatsan) · [论文 PDF](https://www.usenix.org/system/files/osdi26-srivatsan.pdf)

### 针对的问题

**来源事实/作者主张：** serverless 风格任务经常短算长等；传统进程或 MicroVM 快照恢复需要数百毫秒，开发者只好预先把程序人工拆成函数和显式状态，既妨碍细粒度调度，也难以把执行迁移到数据位置。

**本项目工程推断：** Agent 等待模型、工具、人审或外部事件时，如果只能保持 worker 或从顶层重跑，就会在资源占用与恢复正确性之间二选一。

### 原设计

Arca 把 continuation capture 做成 OS 核心服务：程序在 I/O 边界返回一个 effect（期望的外部操作）与 callback continuation，effect handler 执行 I/O，之后恢复 continuation。论文报告 Arca 的 snapshot/resume 为 2.55 微秒、缩略图工作负载相对非 continuation 方案加速 50–60 倍；这些是作者实验。状态可暂停、迁移或复制，但 socket 状态、共享可变内存和广泛 POSIX 兼容性构成根本或工程限制。

### 对 Agent 服务器的采用设计

不移植 Arca OS，而采用其“计算与 effect 分离”边界。把每次模型/工具/人审等待编译为 `continuation_record`：包含不可变 workflow 版本、下一状态、局部变量引用、artifact 哈希和 effect 请求；调度器可在任意兼容 worker 恢复。外部 I/O 只由 effect gateway 执行，并要求 capability、幂等键和结果收据。continuation 中禁止保存 socket、线程对象、明文凭证和进程地址。

### 验收不变量

故障注入：在工具请求已发出、结果未写回时杀死 worker，并把 continuation 迁移到另一节点恢复。必须满足：恢复后的逻辑状态与单机无故障执行相同；同一 effect 幂等键不产生第二个外部副作用；快照不包含不可迁移句柄或密钥；等待期间 worker CPU/内存租约可释放。

### 边界与风险

Arca 是研究原型，只有部分 POSIX 支持且不支持共享可变内存；其微秒数据不能直接套用到数据库持久化的 Agent continuation。真正落地应保存逻辑状态而非本机内存镜像，并接受比论文更高的持久化延迟以换取可审计与兼容性。

## 4. StriaTrace：常开骨架 trace，异常时才提高细节

**评分：96/100**（来源 25、问题 20、架构 24、证据 15、服务端价值 12）  
**原始来源：** [OSDI 2026 正式论文页](https://www.usenix.org/conference/osdi26/presentation/wu-haonan) · [论文 PDF](https://www.usenix.org/system/files/osdi26-wu-haonan.pdf)

### 针对的问题

**来源事实/作者主张：** 在线 LLM 推理的 TTFT/TPOT 偶发尖峰即可违反 SLO；全量 CPU/GPU profiler 开销过高，训练侧以秒或分钟发现持久 straggler 的工具又抓不到单次慢 token。工程师常被迫加日志、重新发布并等待复现。

**本项目工程推断：** Agent 服务若只有请求总耗时，就不能区分模型排队、KV 读写、跨进程同步、工具等待和 orchestrator 停顿；但每步全量采样会反过来伤害尾延迟。

### 原设计

StriaTrace 只在约十个关键跨机/跨进程同步点做常开 tracing，GPU 侧聚焦关键路径的 kernel 与 memory copy，异常时再采集 py-spy 栈等细节；动态回归 roofline 与相关性诊断用于定位原因。作者报告相对替代方案降低 97.8% tracing 开销，生产周期中诊断数百次异常、覆盖 19 类根因。CPU 采样可能漏掉微小停顿，CUDA driver/runtime 细节也因开销而被省略。

### 对 Agent 服务器的采用设计

为 `request → orchestrator → model gateway → scheduler → inference worker → tool gateway` 定义最小同步点集合，常开记录阶段开始/结束、队列时间、版本和资源维度；按模型、上下文长度、batch 与租户类别维护动态基线。只有超过基线或 SLO 的 request 才触发有限时窗的细粒度栈、GPU 或工具诊断；所有升级采样都写入独立诊断预算。

### 验收不变量

注入模型排队、KV 存储回退、CPU GIL 争用和慢工具四类故障。必须满足：常开 tracing 对 P99 的额外开销低于 2%；异常请求在诊断 SLO 内定位到正确层级；每条选中请求的关键同步路径连续；正常请求不产生高细节 trace；采样失败不影响业务请求完成。

### 边界与风险

论文面向 vLLM 推理层，不覆盖完整 Agent 工作流；97.8% 和根因数量均是作者环境结果。动态基线可能把缓慢劣化当成正常，异常触发也可能遗漏一次性短故障，因此必须保留独立 SLO 告警和少量随机审计样本。

## 5. AWS Support Companion：每个 Agent 依赖都要有超时、降级与刷新契约

**评分：92/100**（来源 24、问题 18、架构 22、证据 14、服务端价值 14）  
**原始来源：** [AWS 官方技术博客](https://aws.amazon.com/blogs/machine-learning/build-an-ai-powered-aws-support-companion-with-amazon-bedrock-agentcore/) · [官方样例仓库](https://github.com/aws-samples/sample-support-agent-with-agentcore)

### 针对的问题

**来源事实/作者主张：** 一次支持调查在控制台、日志、文档、社区和工单间切换，开始处置前可耗费 30–45 分钟。实现中又有三个明确运行时故障：MCP 服务顺序初始化增加冷启动；Memory 读取可能阻塞主请求；Gateway JWT 一小时到期后产生间歇调用失败。

**本项目工程推断：** Agent 平台的“集成完成”不等于生产可用；每个远程依赖都必须声明是否关键、等待多久、如何降级和何时刷新。

### 原设计

样例将容器化 Agent Runtime、三个 MCP server、AgentCore Gateway、Memory、API Gateway/Cognito/WAF、Guardrails 和 CloudFormation 分层。MCP 客户端用 `asyncio.gather(..., return_exceptions=True)` 并行初始化；Memory 只取最近三轮且限时 2 秒，超时则无记忆继续，响应后异步保存；Gateway token 每次调用前检查，并在到期前 5 分钟刷新。部署脚本还检查 CloudTrail、模板和临时凭证，运行侧配置最小 IAM、PII 脱敏和审计。

### 对 Agent 服务器的采用设计

建立 `dependency_contract`：对每个模型、MCP、memory、identity 和 guardrail 声明 `criticality/timeout/retry/fallback/token_refresh_margin/circuit_breaker/audit_fields`。启动阶段并行发现，但在准入完成时冻结本次 run 的工具清单版本；非关键依赖降级必须进入响应 metadata 与 trace。令牌刷新由 identity sidecar 负责，Agent 代码只拿短期 handle；高权限工具必须经过策略与人审，不能因故障降级而绕过。

### 验收不变量

故障注入：让一个 MCP server 不可用、Memory 超过 2 秒、Gateway token 距过期 4 分钟、Guardrail 返回错误。必须满足：非关键依赖故障时请求在 SLO 内以显式 degraded 状态完成；令牌在首次失败前刷新；关键安全依赖失败时 fail closed；工具清单版本在单次 run 内不漂移；每个降级和刷新决定都有审计原因。

### 边界与风险

这是 AWS 供应商样例，不是独立性能研究；部分服务受区域、支持计划和费用约束。无记忆降级可能造成语义不一致，异步保存也需要幂等和失败补偿；参考架构只能证明实现路径存在，不能证明默认参数适合本项目负载。
