## 1. Evaluating AI Agents: A production blueprint with Strands and AgentCore

- 原始来源：[AWS 官方生产蓝图](https://aws.amazon.com/blogs/machine-learning/evaluating-ai-agents-a-production-blueprint-with-strands-and-agentcore/)；[官方示例代码](https://github.com/aws-samples/sample-evaluating-agents-on-aws-with-strands-and-agentcore)
- 首次公开：2026-07-23；类型：官方工程博客与代码仓库；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** Agent 可能给出流畅答案，却选择错误工具、传入错误参数，或在同一输入的多次运行中表现不一致。单次离线成功率还会掩盖超时、数据漂移和真实用户行为。Motorway 案例涉及 8 个工具、89 个属性和峰值 1,500 个并发用户；来源称上线前后工具选择准确率从 87% 提高到 98%、任务完成率从 82% 提高到 96%、月度事件从 12 起降至 2 起，这些是厂商与客户的自报结果。

### 原设计

**来源事实：** 蓝图把构建期评测分成三层：确定性的工具使用门槛高于 95%，LLM 裁判评估推理高于 85%，输出质量高于 90%，三层全部通过才能部署。每个测试由 `Experiment`、`Case` 和 `Evaluator` 组成；用 `pass^k` 衡量连续成功概率，并用 actor 模拟多轮用户。发布依次经过构建、预发布、至少 4 小时影子运行、5% A/B 和生产；生产 OpenTelemetry trace 按 1%—5% 采样，失败案例回灌为回归测试。

### 对 Agent 服务器的采用设计

**工程推断：** 建立不可变 `EvaluationCase`，至少包含用户目标、允许与禁止的工具轨迹、预期业务结果收据、租户、模型/提示/工具/策略版本。第一层只用确定性断言检查工具、参数、权限和副作用；第二、三层的模型裁判必须以人工校准集和固定版本约束。每个候选版本运行多次，以 `pass^k` 而非平均分过门。发布状态机固定为离线评测、无写权限影子、受限 canary、全量；任何真实失败都必须绑定 trace 和外部结果收据，生成版本化回归案例。

### 验收不变量

- 任一评测层未达到版本化阈值，候选版本不得进入下一状态；改动模型、提示、工具 schema、策略或裁判版本后必须重跑受影响案例。
- 同一候选必须连续通过规定的 `k` 次试验；报告必须同时保存单次分布和 `pass^k`，不能用平均值掩盖不稳定性。
- 影子流量不得获得生产写能力；偏差超过门槛或 canary 业务结果恶化时，发布自动暂停并回退到已知良好版本。
- 每个生产失败都能关联输入、完整工具轨迹、版本集合和业务结果收据，并进入不可变回归集；仅有模型自述不能标记任务完成。

### 边界与风险

阈值和改善数据来自 AWS 与客户案例，不是跨行业通用基准；模型裁判会漂移并可能与被评模型共享偏差。影子流量若调用真实外部系统仍可能产生副作用，因此必须先做权限剥离或幂等沙箱。评测覆盖只能降低已知风险，不能证明未覆盖任务安全。

## 2. How Outtake built a cyber investigator on Claude

- 原始来源：[Anthropic 与 Outtake 官方工程案例](https://claude.com/blog/how-outtake-built-a-cyber-investigator-on-claude)
- 首次公开：2026-07-22；类型：官方客户工程案例；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 13，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 网络调查任务的中位运行时间为 16 分钟，常持续一小时以上，最长约两小时。长运行过程中上下文会压缩，Agent 需要临时创建工具、访问互联网并处理不可信内容；若只依赖会话文本，压缩后会丢失证据与计划，若把所有规则塞入提示，又难以保证关键约束不被遗忘。

### 原设计

**来源事实：** Outtake 先把专家调查标准变成原型，再用 Claude Agent SDK 建立控制 memory、context、filesystem 和 session 的 harness，并以紧密评测循环迭代。文件系统保存证据和工作记忆，即使上下文压缩仍可继续；harness 硬编码不可违背的不变量，提示只提供建议。Agent 可建议新工具，由独立编码 Agent 构建并测试，最终仍需人工审查。外部执行放入称为 blastbox 的隔离环境，并在获得互联网访问前设置检查点。

### 对 Agent 服务器的采用设计

**工程推断：** 将编排不变量与模型可自由规划部分分离：harness 固定阶段状态机、预算、出口策略、证据格式和终止条件；模型只能在阶段内部选择下一步。运行记忆写入追加式 artifact 清单，文本压缩后依据清单和 checkpoint 恢复，而不是让模型重述历史。临时工具先进入隔离构建队列，经过静态检查、单元测试、能力声明和人工批准后才可加入该 run 的冻结目录；外部访问经 egress broker 按目标和用途授权。

### 验收不变量

- 在任意压缩点或进程终止点恢复后，artifact 清单、证据哈希、剩余预算和阶段状态必须一致，已完成外部动作不得重跑。
- harness 的出口、租户隔离、总时长和高风险动作规则不能被提示、临时工具或模型生成代码覆盖。
- 新工具未通过测试、能力审查和人工批准前不得进入执行目录；批准只绑定该工具摘要、版本和当前 run。
- 每个 run 只能以带证据报告、明确失败或预算耗尽终止；“模型认为已完成”不能跳过证据完整性检查。

### 边界与风险

这是 Anthropic 与客户联合案例，运行时长、效果和隔离能力均未独立验证；blastbox 没有公开完整实现。文件系统记忆若缺少租户键、加密、保留期和完整性校验，会把上下文问题变成持久化泄露问题。临时工具自动生成仍可能把攻击内容编译成能力，人工终审不能替代执行时策略。

## 3. OpenSkillRisk: Benchmarking Agent Safety When Using Real-World Risky Third-Party Skills

- 原始来源：[arXiv 预印本](https://arxiv.org/abs/2607.20121)；[作者代码仓库](https://github.com/Miaow-Lab/OpenSkillRisk)
- 首次公开：2026-07-22；类型：预印本与公开代码；总分：**96/100**（来源可信度 23，问题具体性 20，架构深度 23，证据强度 15，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 第三方 Skill 不是普通提示模板，而是能引导 Agent 调用 shell、文件、网络和业务工具的可执行工作说明。作者筛查 175,891 个市场 Skill，识别 263 个风险 Skill，其中 139 个无条件恶意、124 个仅在特定任务上下文中危险，覆盖 7 类风险和 9 个领域。即使最佳测试配置，危险行为成功率仍约为 17%，说明模型识别风险不等于运行时阻止副作用。

### 原设计

**来源事实：** 基准把 workspace、Skill 和 runtime 分开置于隔离沙箱，外部操作由 stub 工具替代，并确定性记录参数、artifact 与事件；在 Codex CLI、Claude Code、Gemini CLI 和 13 个模型组合上测试。论文把模型风险意识与 harness 约束分开评估；主动加载的 Skill guard 能降低攻击成功率，但也会过度拒绝。公开结果中，Claude Code 与 Sonnet 4.6 的攻击成功率为 17.87%，风险意识为 79.85%，安全 F-score 为 80.97%。

### 对 Agent 服务器的采用设计

**工程推断：** Skill 市场只接收签名、内容寻址的 `SkillPackage`，记录来源、依赖、版本、声明能力和测试证据。安装期静态与语义扫描只能决定隔离级别，不能授予权限；任务开始时根据用户意图、Skill 声明和 Agent 身份计算能力差分，默认拒绝未声明的文件、网络、进程和外部写操作。所有 Skill 在最小权限沙箱运行，真实副作用经独立 broker 执行，并返回可核验业务收据；高风险差分要求绑定输入的人工批准。

### 验收不变量

- 安装或启用 Skill 不能扩大 Agent 身份本身的能力；任何新增能力都必须由独立策略决策和显式授权产生。
- “已提示风险”或模型口头拒绝不能替代强制门；测试中让模型忽略提示时，沙箱和 broker 仍必须阻止越权副作用。
- 每个包摘要、来源、声明能力、扫描器版本和运行时实际调用可串成审计链；包内容变化后原批准立即失效。
- 同一 Skill 必须同时通过无条件恶意、合法任务中的条件风险和误报测试；拒绝率过高也不得以关闭强制门来修复。

### 边界与风险

这是预印本，尚无正式接收证据；外部操作主要由 stub 模拟，不能完全覆盖真实系统的竞态、身份缓存和不可逆副作用。固定 CLI 与云模型版本会迅速过时，市场样本也不代表私有 Skill。基准适合设计准入与运行时测试，不应被解释为某个模型或扫描器已经提供充分安全保证。

## 4. Detecting silent agent failures with Amazon Bedrock AgentCore optimization

- 原始来源：[AWS 官方工程博客](https://aws.amazon.com/blogs/machine-learning/detecting-silent-agent-failures-with-amazon-bedrock-agentcore-optimization/)
- 首次公开：2026-07-23；类型：官方工程博客；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 13，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 基础设施指标可以全部健康，Agent 却没有真正修改订单、在库存 API 超时后声称有货，或绕过人工批准。这类故障通常没有异常和 5xx，传统可用性告警无法发现。来源展示的示例中，10 个会话里有 1 个财务回答没有工具调用支撑，说明结果核验需要跨模型、工具和子 Agent 的完整行为轨迹。

### 原设计

**来源事实：** 分析器读取 trace，为每个 session 独立提取行为属性，再跨会话聚类、总结并按影响占比排序。会话图连接模型推理、工具和子 Agent span；根因分析先剪除与异常无关的分支，再生成解释。系统覆盖 11 类行为问题，同时提供意图聚类和分层执行摘要，可按端点或 CloudWatch 日志运行一次性或周期任务，并设置过滤、采样和 IAM。

### 对 Agent 服务器的采用设计

**工程推断：** 统一 span 契约至少包含 `run/session/tenant/agent/tool`、输入输出摘要、版本、策略判定和业务结果收据。在线完成判定先检查关键业务收据；异步分析器对冻结时间窗中的会话独立提取属性，之后再做跨会话聚类，防止多数模式污染单会话事实。根因服务只产生带证据链接的 incident candidate，由规则或人工确认；确认后的失败模式映射到发布评测案例，形成运行—评测闭环。

### 验收不变量

- 订单、转账、审批等关键任务缺少外部系统收据时，即使 HTTP 成功或模型声称完成，也必须标记为 incomplete。
- 每个行为簇都能下钻到原始 session、相关 span 和结果收据；聚类摘要不能成为脱离证据的唯一事实来源。
- trace、聚类和查询按 tenant 强隔离；采样率、分析窗口、模型和分析器版本必须随结论保存。
- 根因自然语言解释只作为待验证假设，不得自动修改策略或生产代码；确认事件必须回灌确定性或可校准的回归检查。

### 边界与风险

来源是 AWS 托管产品说明，示例只有 10 个会话，检测效果与成本没有独立评估。采样可能漏掉低频高损故障，聚类也可能把不同原因合并；自然语言根因会产生误导性归因。敏感输入进入集中 trace 后扩大数据治理面，需要字段级脱敏、最小保留期和受控下钻。

## 5. The Blueprint: How Voicify makes AI-enabled ordering a delight for customers

- 原始来源：[Google Cloud 与 Voicify 官方客户案例](https://cloud.google.com/blog/topics/customers/bringing-delight-to-customer-phone-calls-with-ai)
- 首次公开：2026-07-23；类型：官方客户工程案例；总分：**92/100**（来源可信度 24，问题具体性 20，架构深度 21，证据强度 13，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 电话订餐同时要求极低首字延迟、节假日流量尖峰、POS 事务精确性和合规；任何停顿、限流或错单都会让用户挂断或门店返工。来源称系统必须在提交前对照 POS 构建并校验订单，并把交易精确性目标描述为 100%。Voicify 还称感恩节前的高峰未发生节流、成本下降 25%—30%、客户上线从 1—2 周缩短到 1—2 天，这些均为客户自报。

### 原设计

**来源事实：** 会话编排层理解通话、构建订单、依据 POS 规则校验后才提交；模型使用 Gemini Flash，并从 AI Studio 迁移到 Vertex AI 和企业 Agent 平台。容量采用 provisioned throughput 与 premium pay-as-you-go 组合，以固定容量承接基线、弹性容量处理尖峰。来源强调安全、数据驻留和管理能力，但没有披露精确延迟分位数、故障转移拓扑或事务协议。

### 对 Agent 服务器的采用设计

**工程推断：** 将实时会话与交易提交拆成两个控制回路：语音入口按租户分配预留与突发容量、并以首字延迟和掉线率做背压；订单状态机则固定为 `draft → POS-validated(version) → submit(idempotency_key) → receipt`。模型只能提出结构化订单变更，确定性规则服务负责价格、库存、门店能力和总额；提交器在超时后先按幂等键查账，不能直接重试。降级策略应优先缩短回答、转人工或排队，而不是静默丢弃事务。

### 验收不变量

- 每个租户持续观测首字延迟 P95/P99、掉线率、突发容量和限流；超门槛时先触发已定义降级，不能让请求无界排队。
- 提交使用冻结的 POS 版本、规范化订单摘要和幂等键；响应总额必须与最终 POS 收据一致，模型文本不能覆盖确定性结果。
- 在校验后、提交中和收据落盘前分别杀死进程，恢复后订单最多提交一次，并能判定已提交、未提交或需人工处理。
- 会话音频、转录、支付与门店数据始终按租户、地域和保留期隔离；弹性容量不能把请求路由到不允许的区域。

### 边界与风险

这是 Google Cloud 与客户联合案例，吞吐、节流、成本和上线周期没有独立验证；“100% uptime”与“100% precision”也没有公开测量窗口和分母。来源不足以证明多区域容灾、exactly-once 或支付合规已经完成。可采用的是容量分层与事务边界，而不是照搬厂商指标。
