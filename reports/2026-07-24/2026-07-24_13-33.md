本轮重新核验上轮留下的 4 篇合格库存，并深审 3 个新候选，最终收录 5 篇。最高推荐是把 Agent 服务器明确拆成 **运行平面、控制平面和证据平面**：运行平面用可恢复游标与分层状态承载长任务；控制平面在输入、Agent 间消息、工具输出、持久化和发布等信任边界做前置判定；证据平面只用环境终态、工具收据和不可变 artifact 判定成功。进程存活、模型自述、厂商侧过滤或单一 guard 分数都不能单独证明任务安全完成。

## 1. AI Teammates: how monday.com runs production AI agents on Amazon Bedrock

- 原始来源：[AWS 与 monday.com 官方生产案例](https://aws.amazon.com/blogs/machine-learning/ai-teammates-how-monday-com-runs-production-ai-agents-on-amazon-bedrock/)
- 首次公开：2026-07-22；类型：官方工程博客与生产案例；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 同一个工程 Agent 同时接收 Slack `@mention`、monday 任务和 GitHub PR review；若每个入口各建一套 Agent，会出现三个会话、三份记忆和三条恢复路径。运行侧还面临 Bedrock 节流、pod 崩溃或迁移、真实 CI 依赖与本地测试不一致，以及 Agent 打开 PR 后没有团队认领。monday.com 称其每工程师 PR 吞吐提高超过一半、约五分之一 PR 被自动标准门退回、人工覆盖率在低个位数，这些均为客户自报数据。

### 原设计

**来源事实：** 所有外部触发先进入 SNS，再按团队和路由键扇出到 SQS；EKS consumer 定位会话并交给对应 runner pod。队列提供重试、死信、Bedrock 节流时的背压和发布前一天事件重放。系统刻意分三类状态：ElastiCache 保存当前任务、run cursor、分布式锁、heartbeat 和消息日志；EFS 保存 session workspace、仓库、消息与跨会话 `MEMORY.md`/diary，使新 pod 能挂载后继续；S3 以 session ID 保存最终 transcript、snapshot、artifact 和 eval，作为耐久审计。每个活跃会话一个 EKS pod，远程 sandbox 在人工审查前运行真实依赖、检查和生产流量重放；确定性标准、Agent 近期评测、同类变更历史 revert 率与 sandbox 结果共同决定是否自动合并。

### 对 Agent 服务器的采用设计

**工程推断：** 建立统一 `RunEnvelope`，所有入口只生成带 `event_id`、`tenant/team`、`agent_id`、`session_id` 和幂等键的事件，路由到同一会话队列。协调状态只放可重建的 cursor、租约、heartbeat 和待办；可恢复工作目录按 session 挂载，并用 fencing token 防止两个 runner 同时写；最终证据进入只追加 artifact store。runner 获得有期限的会话身份和秘密，不把长期凭据写入工作盘。发布控制器消费 sandbox 收据、确定性规则结果和版本化历史风险，只在全部证据闭合时自动推进。

### 验收不变量

- 同一外部事件重复投递、worker 在处理前后崩溃或队列重放时，业务动作最多生效一次；每次尝试都能关联同一 `event_id` 和幂等键。
- 任一时刻同一 session 只有持有最新 fencing token 的 runner 可写工作状态；旧 pod 复活后必须被拒绝，不能覆盖新 cursor。
- 在 runner、缓存或节点分别故障后，系统能从工作盘和事件日志恢复到最后确认步骤；已完成工具副作用必须从收据重建，不能重新猜测并执行。
- 未获得 sandbox、确定性标准、身份/权限和 artifact 完整性收据的变更不得自动合并；模型分数不能覆盖任一硬门失败。
- 队列年龄、死信数、每会话积压、模型限流和恢复耗时必须有租户级 SLO；过载时通过背压和优先级降级，不能无界扩容或丢事件。

### 边界与风险

文章由 AWS 与 monday.com 联合发布，规模、效果和可靠性没有独立验证，`monday-agent-sdk` 也未开源。EFS 的共享工作区虽便于 pod 迁移，但来源没有说明多 writer fencing、租户隔离、快照恢复或区域灾备；“每活跃会话一个 pod”在大量休眠会话下可能成本过高。可采用的是状态职责分离与证据门，不是照搬具体云服务。

## 2. Safety Testing LLM Agents at Scale: From Risk Discovery to Evidence-Grounded Verification

- 原始来源：[arXiv 预印本](https://arxiv.org/abs/2607.01793)；[论文 HTML](https://arxiv.org/html/2607.01793)；[作者代码仓库](https://github.com/Yunhao-Feng/Vera)
- 首次公开：2026-07-02，当前 v2 为 2026-07-04；类型：预印本与公开代码；总分：**98/100**（来源可信度 23，问题具体性 20，架构深度 25，证据强度 15，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 许多 Agent 安全测试把危险请求、模型口头同意或某次工具尝试直接当成安全事故，却没有检查环境是否真的发生了数据泄露、越权写入或资源破坏；静态攻击脚本也会在 Agent 走出预设路径后失效。风险定义、环境实现、Agent adapter 和 verifier 紧耦合，使新增工具或风险需要同时修改多层。Vera 在四个 Agent 框架上报告单通道与多通道攻击执行成功率分别为 90.6% 和 93.9%；这里的高成功率反映测试驱动能实现指定行为，不等于所有执行都是安全漏洞。

### 原设计

**来源事实：** Vera 先从约 800 篇材料维护风险、攻击方法和环境三棵 taxonomy，再组合成 39,078 个候选安全目标，经兼容过滤和去重形成 1,600 个可执行基础场景。每个 case 明确初始状态、目标状态变化和确定性 verifier。运行时为每个 worker 启动隔离的 Docker Compose 环境，MCP gateway 记录工具调用并可向工具结果注入攻击内容；control agent 根据目标 Agent 的实际响应调整后续交互。验证优先级固定为环境终态高于工具调用记录，高于模型响应；同一契约适配 Claude Code、Codex、OpenClaw 和 Hermes。

### 对 Agent 服务器的采用设计

**工程推断：** 把安全测试建模为版本化 `ExecutableCase`：包括初始快照、租户身份、允许和禁止的状态变化、攻击通道、最大步数、环境终态 predicate 与清理策略。测试编译器只生成候选，必须经过 schema 校验、最小人工抽样和 verifier 自测后进入回归库。沙箱 orchestrator 为每个 case 分配独立网络、文件、凭据和端口命名空间；tool gateway 同时保存原始结果、注入后结果和 side-effect receipt。发布门按环境状态判定，模型输出仅在没有更强证据时作为诊断线索。

### 验收不变量

- Agent 口头拒绝后若环境已发生危险改变，case 必须失败；Agent 口头同意但没有产生副作用时不得伪报已造成事故。
- 每个 case 从同一快照和版本集合重跑时，verifier 的确定性结果一致；不一致必须归因为环境、工具、模型或 verifier 版本变化。
- control agent 只能通过声明的测试接口影响目标，不能绕过目标 Agent 直接制造目标状态；所有注入与工具调用都有顺序化日志。
- 沙箱网络、凭据、端口和持久卷按 case 隔离；杀死任一容器后，清理器必须证明没有跨 case 残留和真实外部副作用。
- 新风险或工具接入不得要求修改既有 Agent 核心运行逻辑；只通过 adapter、case schema 和 verifier 扩展，并在发布前跑兼容性集。

### 边界与风险

这是处于双盲评审中的预印本，尚无正式接收证据；公开仓库目前历史很浅，本轮未独立重跑大规模实验。生成的场景和 verifier 本身可能误配，良性执行成功率仅 70.5% 也提示环境或多谓词 oracle 可能过严。每个会话包含多容器和高 token 消耗，生产 CI 需要按风险分层抽样，不能把完整攻击搜索放入每次提交。

## 3. Best practices for applying Amazon Bedrock Guardrails to code generation workflows

- 原始来源：[AWS 官方工程博客与代码示例](https://aws.amazon.com/blogs/machine-learning/best-practices-for-applying-amazon-bedrock-guardrails-to-code-generation-workflows/)
- 首次公开：2026-07-23；类型：官方工程博客；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 15 个并发开发者各生成约 5,000 字符代码，若使用默认每 50 字符一次的流式 guardrail 且启用三类 safeguard，会形成每秒约 1,500 次评测请求，导致 `ThrottlingException`、输出停顿、成本和延迟上升。根因不是单纯 quota 不足，而是把短对话的逐块扫描套在长代码与 Agent loop 上；同时重复扫描 system prompt、tool schema 和历史内容，却没有优先保护代码落盘、执行和提交这些真正的风险跃迁。

### 原设计

**来源事实：** 文章建议用独立 `ApplyGuardrail` API 在自然信任边界选择性验证：每轮只扫新增用户内容；流式输出按 1,000 字符批次；最终聚合 artifact 做一次完整检查；文件写入或 commit 前再做强校验；工具层只拦截 `write_file`、`execute_code`、`run_command` 等危险能力；中间推理不扫描。已成功检查的文件按内容 SHA-256 缓存，内容变化即失效。来源称 1,000 字符流式间隔相对默认 50 字符最多减少 20 倍评测频率，这是按计费与调用单位推导，不是独立生产基准。

### 对 Agent 服务器的采用设计

**工程推断：** 将 guardrail 从模型调用参数提升为独立 `ArtifactPolicyGateway`。每次判断绑定 `tenant`、artifact hash、来源、目标动作、策略/规则/模型版本和过期时间；只对跨越 `untrusted input → model`、`draft → persistent artifact`、`artifact → execution`、`execution → external side effect` 的内容做同步硬门。流式检查用于尽早反馈，不作为最终许可；commit、shell、部署与外部写操作必须重新验证完整规范化 artifact，并把判定收据交给执行 broker。

### 验收不变量

- 未取得与完整 artifact hash、目标动作和当前策略版本绑定的 `allow` 收据，文件不得进入持久仓库，代码不得执行或部署。
- 同一不可变内容在缓存有效期内只评测一次；内容、策略、模型、工具 schema 或风险级别任一变化时缓存立即失效。
- 注入 15 个并发长输出并打开多类 safeguard 时，评测请求速率受预算和背压约束，不能导致模型流无限停顿；超载必须 fail closed 或转人工。
- 抽取 50 字符边界、1,000 字符边界和完整 artifact 三类对抗样本，最终门的安全判定不得因流式分块方式变化。
- 内容过滤通过不等于代码安全；执行前仍必须通过静态分析、测试、秘密扫描、沙箱和最小权限策略。

### 边界与风险

这是 AWS 产品指导而非独立安全评估；正则风险分类和内容 guardrail 可被规避，也不能理解完整代码语义。延后到 commit 边界会降低实时提示，但若前置门过严又会恢复吞吐问题。最关键边界是内容检查绝不能替代执行隔离、依赖供应链检查和真实副作用授权。

## 4. ChannelGuard: Safe Models Do Not Compose into Safe Multi-Agent Systems

- 原始来源：[arXiv 预印本](https://arxiv.org/abs/2607.19430)；[论文 HTML 与复现实验说明](https://arxiv.org/html/2607.19430)
- 首次公开：2026-07-20；类型：预印本；总分：**96/100**（来源可信度 23，问题具体性 20，架构深度 24，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** planner、worker、tool、memory、verifier 和 synthesizer 之间的每条文本通道都可携带攻击指令；只守用户输入，会漏掉工具结果和共享记忆。更隐蔽的问题是“安全机制替换”：某个后端上攻击成功率为零，可能完全依赖供应商侧随机过滤，而不是应用自身控制；切换模型供应商后相同系统会失去保护。论文在 2,100 条 trace 上展示了这种归因差异。

### 原设计

**来源事实：** ChannelGuard 在用户到 planner、planner 到 worker、worker 到 memory/verifier、tool 到 worker、memory 读取到 worker、worker 到 synthesizer 等六类边界放置 gate。每个 gate 将句子 embedding 与攻击 phrase bank 比较，确定性输出 pass、compress 或 block；block 立即短路，不继续调用下游模型。工具输出门在三种模型后端上都由应用层拦截 30/30 Tool Poisoning；同时每条 trace 保存是应用 gate、供应商 filter、verifier 还是模型自身阻止了攻击。作者也明确报告白盒自适应改写在两种系统上均有 0.667 ASR，静态 phrase bank 不是通用防御。

### 对 Agent 服务器的采用设计

**工程推断：** 不照搬静态 phrase bank，而是先建立统一 `MessageEnvelope`：包含生产者/消费者身份、信任级别、来源 artifact、内容 hash、可见字段和策略版本。所有跨 Agent、tool→Agent、memory→Agent 通道必须通过应用所有的 `ChannelPolicyGateway`；低成本确定性规则先短路，语义 classifier 和独立 verifier 只处理灰区。每次决策写入归因账本，区分应用控制、供应商过滤、模型拒绝和人工批准，发布指标按机制分层而非只看最终 ASR。

### 验收不变量

- 关闭供应商侧过滤或切换模型后端时，应用层必须仍能达到已声明的关键通道阻断率；任何下降都触发发布失败。
- 每个跨边界消息都有生产者、消费者、来源 hash 和 gate 收据；无法归因的文本不得进入高权限 worker、共享 memory 或 synthesizer。
- 对工具投毒、记忆投毒、慢漂移叙事和白盒改写分别注入；报告必须同时给最终结果与首个阻断层，不能把模型偶然拒绝算成应用保证。
- gate 的 block 必须在下游模型或工具调用前生效；重试和恢复不能绕过已记录决策，也不能把被拒消息换一个通道重送。
- 误拒率、漏检率、延迟和短路节省按通道独立观测；阈值变化必须版本化并重跑良性保真集。

### 边界与风险

论文仍在评审中，代码与数据链接是匿名 artifact，本轮未独立复现；主结果使用单 seed、mock tool 和英文静态 phrase bank，部分改进样本量不足以显著。作者已证明白盒改写和叙事式慢漂移能绕过门，且某些通道 gate 在当前语料上几乎没有判别力。因此可采用的是“全通道覆盖、机制归因、供应商反事实”三项架构原则，而不是把 embedding 阈值当成安全边界。

## 5. JANUS: Foreseeing Latent Risk for Long-Horizon Agent Safety

- 原始来源：[arXiv 预印本](https://arxiv.org/abs/2607.19913)；[论文 HTML](https://arxiv.org/html/2607.19913)；[作者代码仓库](https://github.com/xiongyuaay/JANUS)
- 首次公开：2026-07-22；类型：预印本与公开代码；总分：**93/100**（来源可信度 24，问题具体性 20，架构深度 23，证据强度 14，Agent 服务端价值 12）

### 针对的问题

**来源事实/作者主张：** 反应式 guard 只检查当前动作；在长任务中，真正危险的全局环境修改、数据外传或资源耗尽往往由一串早期看似合理的步骤逐渐形成，到最后一次工具调用才阻止已经太迟。论文示例是用户早先要求依赖仅限虚拟环境，Agent 后续却修改全局 Python 环境。风险还可能来自用户、工具/邮件/记忆等环境，或 Agent 对含糊目标的错误假设。

### 原设计

**来源事实：** JANUS 用 Manager、Instructor、ToolDesigner、Grader、EnvInjector 和 Simulator 合成带风险起点、工具 schema、评价标准和未来 continuation 的长轨迹，不调用真实工具；Vanguard 在运行时先根据轨迹前缀生成安全相关未来摘要，再结合前缀和预测做 adjudication。训练用 coupled anticipation/adjudication reward，让未来预测服务于动作前安全判断。论文称四个 benchmark 上保护率平均提高 15.9 个百分点、良性完成率提高 5.1 个百分点；消融中去掉 anticipation 后三项代表 benchmark 的平均 ASR 从 0.072 升至 0.148。

### 对 Agent 服务器的采用设计

**工程推断：** 只把预测 guard 放在高影响动作的 preflight 阶段，不让它成为唯一执行授权者。`RiskContext` 应包含当前阶段、不可变用户约束、已完成副作用收据、候选动作、资源/权限差分和剩余预算；guard 输出风险类别、可解释未来假设、置信度与建议动作。低风险继续，中风险缩小能力或要求额外证据，高风险转人工或确定性 policy deny。预测结果和最终真实状态回写到证据平面，用于校准而不是自动在线学习。

### 验收不变量

- 文件删除、全局依赖修改、外部发送、支付和权限变更等高影响动作必须在执行前取得确定性策略许可；预测 guard 只能收紧，不能覆盖硬拒绝。
- 从真实历史截取不同长度前缀回放，guard 必须在副作用发生前达到版本化召回门槛；同时以良性任务完成率约束过度阻断。
- 预测摘要必须与输入 prefix、模型和策略版本绑定，并在事后对照真实 continuation；无法校准的自然语言解释不得成为审计事实。
- guard 超时、不可用或低置信度时按风险分级 fail closed 或转人工，不能静默放行高影响动作。
- 新工具、权限或运行环境上线前必须加入未见分布测试；生产只做受控采样和人工确认，不能用线上危险行为直接自训练。

### 边界与风险

JANUS 的主要贡献是预测 guard 的训练方法，不是完整 Agent 服务器；本轮只采用其“动作前看轨迹未来”的控制位置。训练数据来自多 Agent 模拟而非真实工具，固定 benchmark、Agent backbone 和风险分布不能证明对新工具或自适应攻击有效。预测模型会幻觉未来、产生误拒或被操纵，因此必须置于确定性 policy 与最小权限执行器之间，不能直接掌握副作用能力。
