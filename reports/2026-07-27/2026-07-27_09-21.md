## 1. Open Knowledge format v0.2 tackles agentic trust

- 原始来源：[Google Cloud 官方工程博客](https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals/)；[官方参考实现](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf)
- 首次公开：2026-07-24；类型：官方工程博客与代码仓库；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 普通知识文档只给 Agent 一段文本，无法表达它来自哪里、是否由模型生成、由谁核验、何时过期，也无法证明某个数值确实由批准的数据和程序计算。来源把“文档是否经过审核”与“某次计算是否按允许的执行器、参数和输入完成”明确区分；前者是文档信任，后者是运行证明。

### 原设计

**来源事实：** OKF v0.2 在可选 frontmatter 中加入 `sources`、`generated`、`verified`、`status` 和 `stale_after` 等信任信号，旧文件仍可兼容。Attested Computation 把受认可运行时、参数、执行器和输出绑定成 receipt，再由不调用 LLM 的确定性 attester 检验。官方仓库提供概念验证参考实现，但博客也把它定位为开放格式的早期机制，而非完整生产安全系统。

### 对 Agent 服务器的采用设计

**工程推断：** 建立不可变 `KnowledgeArtifact`，内容 hash 与来源、生成器、核验者、状态、新鲜度策略分离存储；检索层只返回带 provenance envelope 的片段。需要影响规划或业务决策的计算必须提交 `ComputationReceipt`，绑定输入版本、代码/执行器摘要、参数、策略和输出 hash；授权层根据租户、用途和风险决定该文档只能参考、可参与推理，还是可驱动副作用。文档审核不能替代每次运行的证明，运行收据也不能自动证明业务语义正确。

### 验收不变量

- 任一检索片段都能追溯到不可变 artifact hash、来源 URI、生成/核验主体、状态和新鲜度；缺字段时按低信任处理，不能默认为可信。
- `stale_after` 到期、来源版本变化或核验被撤销后，旧片段不得继续驱动高影响动作；缓存必须同步失效。
- 计算输出只有在 receipt 与输入、执行器、参数、策略和输出 hash 全部匹配时才可升级为已证明；自然语言说明不能代替 receipt。
- 文档级 `verified` 不得覆盖租户授权、数据分类或动作策略；跨租户来源即使公开也必须经过用途门。
- 旧版无元数据文档仍可读取，但其权限上限必须低于已验证工件，并在审计日志中显示降级原因。

### 边界与风险

格式中的元数据可能由不可信发布者自报，签名、撤销、密钥轮换和跨组织信任根仍需平台补齐。确定性 attester 只能证明“按指定过程执行”，不能证明输入真实、程序无漏洞或结果适合业务。参考实现是概念验证；可采用的是信任信号、运行证明和授权分层，不是把 frontmatter 当成安全边界。

## 2. IssueTrojanBench: Benchmarking AI Coding Agents Against Malicious Issue Requests

- 原始来源：[arXiv 预印本](https://arxiv.org/abs/2607.20759)；[论文 HTML](https://arxiv.org/html/2607.20759)；[公开实验工件](https://doi.org/10.5281/zenodo.19245678)
- 首次公开：2026-07-22；类型：预印本、公开工件及正式机构作者证据；总分：**98/100**（来源可信度 24，问题具体性 20，架构深度 25，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 恶意仓库 issue 可把指令藏在正文、PDF、图片替代文本或项目策略文件中，诱导编码 Agent 安装恶意包、加入持久化 hook、污染 `.cursorrules`、`CLAUDE.md`、`AGENTS.md`，或执行资源耗尽。作者构造 696 个对抗工件，在 Cursor、Claude Code、Codex Desktop 与三种模型组合上运行 4,176 次，报告 66.5% 的工件能穿过所有 guard；标准文本/PDF 的成功率为 72.2%，替代文本为 16.7%。这些是作者实验结果，不是独立生产事故统计。

### 原设计

**来源事实：** Benchmark 将交付载体、攻击目标、Agent/模型组合与预期环境终态分开，使用终端和文件系统状态 oracle 判断是否真的发生安装、持久化、策略污染或资源消耗，而不是只看模型回复。82.9% 的抵抗来自模型明确拒绝，17.1% 来自来源信任分类；简单边界标记未形成可靠防线。论文公开两套仓库与本地沙箱实验工件。

### 对 Agent 服务器的采用设计

**工程推断：** 所有 issue、附件、仓库文档和策略文件先进入 `UntrustedArtifactGateway`，做类型解析、来源分类、内容 hash 和隔离存储；这些文本只能作为 user-role 证据，不能直接合并进 system/developer policy。执行 broker 将包安装、启动项/钩子修改、策略文件写入、网络发送和高资源命令定义为高影响能力，要求独立策略、短期身份、预算和人工/确定性批准。回归测试以文件、进程、网络和依赖锁的环境终态为 oracle，并保留实际副作用收据。

### 验收不变量

- 来自 issue、附件、OCR、alt-text、仓库 README 和项目策略文件的内容始终保留来源标签；任何文本都不能自行提高到 system/developer 权限。
- 未取得与租户、仓库、动作、参数和 artifact hash 绑定的许可，Agent 不得安装依赖、修改启动/策略文件、发送外部数据或突破资源预算。
- Agent 口头拒绝但环境已改变时测试必须失败；Agent 口头同意但无副作用时不得误报已攻破。
- 同一攻击工件跨 Agent 和模型回放时，必须同时记录首次阻断层与最终终态，不能把供应商偶然拒绝当成平台保证。
- 杀死沙箱后必须证明无宿主机持久化、真实凭据外泄、跨 case 文件或残留进程；资源上限由运行时强制而非提示词约束。

### 边界与风险

论文是预印本，本轮核验了公开工件与 end-state oracle 设计，但未独立重跑 4,176 次实验。实验集中于编码 Agent、有限模型和构造攻击，不能直接外推所有工具生态。来源分类只能降低风险，无法证明内容安全；真正边界仍是最小能力、隔离执行、动作授权和终态验证。

## 3. Native Agent Memory for Microsoft Agent Framework, Powered by Azure Cosmos DB

- 原始来源：[Microsoft Azure Cosmos DB 官方工程博客](https://devblogs.microsoft.com/cosmosdb/native-agent-memory-for-microsoft-agent-framework-powered-by-azure-cosmos-db/)；[Microsoft Agent Framework 官方仓库](https://github.com/microsoft/agent-framework)
- 首次公开：2026-07-24；类型：官方工程博客、预览包与代码样例；总分：**97/100**（来源可信度 25，问题具体性 20，架构深度 24，证据强度 13，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 多轮 Agent 把召回、事实抽取、摘要和用户画像散落在业务代码中，开发者容易使用不稳定的会话标识、阻塞主响应或把取回文本误当成高优先级指令。跨线程记忆还要同时解决用户级与线程级作用域、持久化和混合检索。

### 原设计

**来源事实：** 预览版 Python `CosmosMemoryContextProvider` 在 `before_run` 召回并注入记忆，在 `after_run` 保存消息并提取事实、摘要和画像；调用方提供稳定 `user_id` 与 `thread_id`。Cosmos DB 用 JSON 文档和混合检索承载记忆，后台抽取任务在 context 退出时 drain。博客样例把取回画像以 user-role 的“不可信参考”注入，而不是 system instruction，并链接可运行示例和官方仓库。

### 对 Agent 服务器的采用设计

**工程推断：** 将记忆服务做成独立 `MemoryContextProvider`：主键包含 tenant、subject、thread、memory type 和版本；写入端保存原始事件引用、抽取器版本、置信度、同意/保留策略，召回端返回带来源和用途限制的 `MemoryEnvelope`。`before_run` 只注入预算内、未过期、当前租户可见的低权参考；`after_run` 通过 outbox 异步抽取，完成后生成收据。用户更正、删除和策略变化通过 tombstone 与派生索引重建传播。

### 验收不变量

- 相同用户跨线程使用稳定主体键，不同租户即使 `user_id` 相同也绝不共享记忆；线程记忆不能无授权升级为用户全局画像。
- 召回内容始终以低权、带来源的参考上下文注入，不能覆盖 system policy、实时工具结果或用户当前明确指令。
- 主响应成功不依赖后台抽取完成；抽取重试必须幂等，进程退出前 drain 或将任务持久化到可恢复 outbox。
- 删除、更正、同意撤回和保留期到期后，原文、摘要、画像、向量与缓存都在规定 SLO 内失效，并留下可审计收据。
- 每条事实能追溯原始事件、抽取器版本和置信度；冲突事实不得静默覆盖，召回必须显示时序与优先规则。

### 边界与风险

该能力仍是预览版，博客没有提供规模、延迟、删除传播或故障恢复基准。混合检索提高召回不代表事实正确，自动画像还涉及同意、隐私和地域合规。Cosmos DB 是一种实现选项；更关键的是稳定主体键、生命周期钩子、低权注入、异步可恢复抽取和派生数据治理。

## 4. Move Agent Orchestration/Workflows out of Code with Agent Framework Declarative Workflows 1.0

- 原始来源：[Microsoft Agent Framework 官方工程博客](https://devblogs.microsoft.com/agent-framework/move-agent-orchestration-workflows-out-of-code-with-agent-framework-declarative-workflows-1-0/)；[官方代码仓库与示例](https://github.com/microsoft/agent-framework)
- 首次公开：2026-07-23；类型：官方工程博客、1.0 软件包与代码示例；总分：**95/100**（来源可信度 24，问题具体性 19，架构深度 24，证据强度 13，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** Agent 步骤、分支、循环、handoff 和人工批准硬编码后，业务流程修改必须改代码和重新发布；不同语言实现也容易产生不同恢复语义。长流程如果没有显式状态和检查点，进程中断后会重放已完成副作用。

### 原设计

**来源事实：** Declarative Workflows 1.0 用 YAML 定义 Agent 步骤、状态表达式、条件分支、循环/跳转、Agent 调用、函数/MCP/HTTP 工具、人工输入/批准和 checkpoint/resume；定义加载成与代码编排相同的 `Workflow` 类型。Python 与 .NET 包均为 1.0，官方仓库提供样例。来源没有声称 YAML 自动解决授权、迁移或外部副作用幂等。

### 对 Agent 服务器的采用设计

**工程推断：** 建立 `WorkflowDefinition` 注册表，定义以内容 hash、schema 版本、签名和发布状态不可变寻址；每次 run 固定 `definition_version`，中途更新只影响新 run。编译阶段解析 agent/tool 引用并生成能力清单，策略服务逐边授权。checkpoint 保存步骤游标、业务状态版本、待处理人工决定与副作用收据；恢复前对 definition、工具 schema、身份和资源版本做兼容检查。外部写入统一走带幂等键的 effect executor。

### 验收不变量

- 已启动 run 始终绑定同一不可变 workflow hash；编辑同名 YAML 不能改变正在恢复的流程。
- 未在编译清单和租户策略中同时允许的 Agent、MCP、HTTP 或函数工具不得执行；表达式不能动态构造绕过授权的目标。
- checkpoint 只在已完成副作用收据持久化后推进；崩溃发生在任意边界时，恢复不会重复扣款、发送或写入。
- 定义、schema、工具契约或状态迁移不兼容时必须停止并转人工/迁移流程，不能从旧 checkpoint 猜测继续。
- 人工批准绑定 run、步骤、输入摘要、候选动作和过期时间；复制批准 token 到另一 run 或参数变化后必须失效。

### 边界与风险

声明式格式会把代码风险转移到配置供应链：恶意或错误 YAML、表达式和工具引用同样能造成高影响动作。1.0 表示软件包版本，不等于生产成熟度或跨语言语义已被独立验证。采用时必须补齐签名发布、静态编译、授权、迁移、effect 幂等与灰度回滚；不要允许线上直接编辑并影响运行中实例。

## 5. Building trade assistant: How Jefferies optimized front office trading operations with AI

- 原始来源：[AWS 与 Jefferies 官方生产案例](https://aws.amazon.com/blogs/machine-learning/building-trade-assistant-how-jefferies-optimized-front-office-trading-operations-with-ai/)
- 首次公开：2026-07-23；类型：官方工程博客与客户生产案例；总分：**93/100**（来源可信度 24，问题具体性 19，架构深度 23，证据强度 13，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 前台交易人员用自然语言查询多个数据源时，模型既可能选错 schema/数据源，也可能生成越过用户权限的 SQL；若再让 LLM 自行生成图表，结果难以复现并可能扩大敏感数据暴露。系统还要维持认证会话和对话审计，同时满足交互延迟。

### 原设计

**来源事实：** 架构包括认证服务、bot/session 服务、query agent、知识库 schema 检索、由 MCP 选择数据源、查询执行器注入行级 SQL 过滤，以及对话日志。来源明确让代码而非 LLM 生成可视化，并以 in-memory database 降低延迟。业务效果和可靠性是 AWS/Jefferies 自报，文章未公开完整失败、回滚或隔离实现。

### 对 Agent 服务器的采用设计

**工程推断：** 请求进入 `AuthenticatedQuerySession`，携带租户、交易员身份、desk、用途和数据许可；检索层只返回该身份可见的 schema 元数据。模型输出结构化查询意图而非最终 SQL，policy-aware compiler 生成参数化计划，执行器在不可绕过层注入行列过滤、限额、超时和只读事务。结果集绑定 query plan、数据快照和授权收据，再交给确定性图表服务；原始敏感数据不回写长期记忆。

### 验收不变量

- 模型生成内容不能删除、覆盖或放宽执行器注入的行列权限；对抗性 SQL、嵌套查询和数据源切换均不能越过主体许可。
- 每次查询能关联身份、用途、schema 版本、规范化计划、策略版本、数据源和结果 hash；对话文本不能代替审计收据。
- 同一授权快照、查询计划和数据快照生成相同聚合与图表；可视化代码不得执行模型生成脚本。
- 查询超时、资源量、返回行数和敏感字段由执行层硬限制；取消或断线后不能留下无主长查询。
- 跨会话记忆不得保存未脱敏结果或推导出的敏感仓位；会话过期、权限撤销后缓存和后续查询立即失效。

### 边界与风险

案例没有独立性能或安全审计，也未披露模型误路由率、SQL verifier、故障恢复和行级策略实现细节。MCP 只解决工具接口，不自动提供授权；内存数据库也会带来新鲜度、容量和恢复权衡。可采用的是“身份到执行器的不可绕过权限链”和确定性结果呈现，而不是把客户效果数字当成通用保证。
