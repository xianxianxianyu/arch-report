## 1. Towards a Systems Foundation for Agentic Cloud Management

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.25883)
- 首次公开：2026-07-28；作者机构：香港大学、Microsoft、UIUC；类型：机构预印本与 Azure API 原型验证；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 云管理意图属于会话，但 VM、网络、磁盘、配额等真实状态由多个会话共享。论文给出的最小反例是：Agent A 要永久删除 VM，Agent B 同时要通过“删除再重建”替换同一 VM；无论哪一方的删除先到，另一方都可能把临时失败当作可重试错误，最终删除新 VM 或重新创建本应消失的 VM。现有 IaC 工作区只看见自身工作流，provider 只看见零散 API，冲突的全局意图和失败归因均丢失。

### 原设计

**来源事实：** CloudWeaver 在 provider API 边界拦截操作。权威全局图记录资源、包含/挂载/路由/依赖关系、生命周期、所有权、可见性、配额与意图历史；每个会话只得到策略控制的局部图投影。API parser 将请求变成局部图 delta，再解析为全局 delta 和 transaction descriptor。提交时先按当前全局图重新验证，使用多粒度锁保护拓扑、用 escrow lock 预留 vCPU、子网 IP、共享盘槽位等容量；只有结构与容量都可行时才把 pending delta 写入全局图并调用云 API。失败、异步完成和 drift 会反向更新全局及受影响局部图。六个 Azure API 操作的初步 trace 显示独立操作仍可并发，冲突操作会在 provider 副作用前被阻止并得到带阻塞意图的反馈。

### 对 Agent 服务器的采用设计

**工程推断：** 在 tool gateway 与云 provider 之间增加 `IntentTransactionService`。每个 run 提交带 tenant、session、principal、desired outcome、资源集合和幂等键的 intent；服务端把低层工具调用编译为版本化 `ResourceDelta`。规划读取的是 `LocalResourceView(version)`，执行使用全局版本进行 compare-and-admit；结构权利与可消费容量分开预留。provider 响应先成为 effect receipt，再更新 authoritative graph 并投影给相关会话。冲突返回机器可读的资源、约束、阻塞 intent 和可重试条件，不让模型从普通 404/409/429 猜测。

### 验收不变量

- 并发注入“永久删除”与“删除后重建”同一资源；任一提交序列都只能得到一个显式胜出的 intent，不能由独立重试生成第三种终态。
- session A 的局部图不得出现 B 的私有资源；共享对象在各局部图中的映射必须指向同一全局身份和可验证版本。
- 在 lock plan 计算后、提交前改变拓扑或耗尽配额；旧 descriptor 必须重新验证失败，且 provider 收不到请求。
- `reserved + committed <= capacity` 始终成立；kill coordinator 后，未提交 escrow 可回收，已提交 effect 不得被第二次执行。
- 冲突收据必须包含 blocking intent、资源/容量约束、可重试条件和全局版本；Agent 不得把不可调和冲突作为无界瞬时错误重试。

### 边界与风险

这是预印本，验证仅含三个会话、六个 Azure API 操作，作者明确把大规模 trace、长尾性能和完整 provider 覆盖留作后续工作。云 API 的异步终态、外部绕过写入和 plugin 语义错误仍可能使全局图过期；单一协调层也会成为高价值可用性与权限边界。采用时必须允许只读降级、外部变更 reconciliation、plugin conformance 测试和分片后的跨分片事务策略。

## 2. CodeNib: A Multi-View Data System for Serving Repository Context to Coding Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.25431)
- 首次公开：2026-07-28；作者机构：UC San Diego、Stanford、UC Riverside、USC；类型：机构预印本与系统实验；总分：**98/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 编码 Agent 会反复 grep、读文件、查定义和引用，但词法索引、向量索引、结构图、LSP 与会话历史各有不同的数据布局、新鲜度和输出语义。把它们当成一个“检索工具”会隐藏生命周期成本，也会把旧 commit 的候选、当前 worktree 的位置和任务内历史混为同一证据。每次任务重新探索又浪费 token 和构建时间。

### 原设计

**来源事实：** CodeNib 把不可变 commit 视为基础数据，为每个 commit 独立物化词法、dense 与 structural 视图；所有结果规范化为 repo-relative path、源码范围与记录类型。manifest 记录工件路径、状态、commit、构建配置和支持的操作。更新时，结构图用 Git/LSP 辅助修复，向量通过内容寻址复用，独立 rebuild 只用于事后核验更新结果而不是偷偷修正维护路径。runtime 根据查询计划加载需要的视图，把排序候选、定义/引用位置与 bounded context 保持为不同契约，并可通过 MCP 工具送入 Agent。实验中，静态导航在 1,000 次请求的 632 次可比子集中匹配 live server 的规范化位置，live/static 中位延迟比 4.72；正确匹配独立重建的图和向量更新分别取得 8.67 倍和 25.44 倍中位加速；五个模型中，满足共同定位质量边界的最低 token 策略比 grep/read 少 50%–87% trajectory token。

### 对 Agent 服务器的采用设计

**工程推断：** 为仓库建立 `RepoViewManifest(repo, commit, builder_version)`；每个视图声明输入 commit、config hash、能力、freshness 与地址语义。run 启动时固定 base commit 和 worktree delta，查询响应携带 `EvidenceAddress`、view ID、source hash 和 validity boundary。不可证明增量等价的视图标记 stale，只降级到 rebuild/live provider，不能继续混合返回。context assembler 依据任务预算选择排序片段与结构邻域，历史压缩与仓库证据分开计量；编辑提交后再异步维护下一版本视图。

### 验收不变量

- 对任一返回片段，`hash(read(repo, commit, range)) == evidence.source_hash`；checkout 或 worktree 改变后旧地址不能冒充当前内容。
- 随机注入 rename、delete、跨文件引用和部分构建失败；增量视图若与独立 rebuild 不等价必须标为 stale，不能原子发布半套 manifest。
- kill builder 于词法、向量或图更新之间；旧 manifest 仍完整可读，新 manifest 只有所有必需工件校验通过后才可见。
- 对同一冻结任务比较 raw grep/read 与预构建视图；定位质量不得低于门槛，trajectory token、P95 查询延迟和索引维护成本分别计量。
- MCP 工具结果必须包含 commit 与地址类型；Agent 用旧 commit 的位置执行 edit 时，服务端以 precondition failure 拒绝而不是错改相同行号。

### 边界与风险

论文评测的是定位和上下文供应，不是 patch 正确率；并发生产更新也明确不在范围内。静态导航只在 63.2% 请求上与 live server 形成可比子集，不能把 4.72 倍外推到全部语言与语义查询。论文给出的代码与工件仓库在本轮核验时返回 404，因此实现可复现性尚未验证。物化多视图会增加存储、builder 版本迁移和失效治理成本；仓库权限、secret 过滤和多租户缓存隔离仍需由外围系统负责。

## 3. SkillGate: Cost Efficient Runtime Malicious Skill File Detection in Coding Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.25619)；[SkillGate 公开仓库](https://github.com/awsm-research/skillgate)
- 首次公开：2026-07-28；作者机构：Monash University、University of Melbourne、Transurban；类型：机构预印本、开源 MCP 代理与基准实验；总分：**98/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** Skill 是自然语言指令、资源和脚本的供应链工件，能通过 registry、Git 或 MCP 的 `tools/call`、`resources/read`、`prompts/get` 进入高权限编码 Agent。它不是传统源码包，Semgrep/SCA 等代码扫描器看不懂其中“读取凭据后上传”一类行为指令；一旦加载，恶意内容会影响整个会话。全文件交给 LLM 审核又带来安装时延、费用、敏感内容外发和不稳定误报。

### 原设计

**来源事实：** SkillGate 是可本地部署的 MCP proxy daemon，在 Skill 到达 Agent 前拦截。第一阶段用 530 条规则预筛，其中 428 条来自 MITRE ATT&CK、102 条来自 Sigma；未命中者直接放行。命中者只抽取规则附近的合并窗口交给可配置 LLM judge，而非发送整文件；随后由 policy engine 决定放行、隔离或阻止，并记录 audit log。它以一行配置接入五种编码 Agent。SkillsBench 含 1,500 个真实良性与 150 个手工恶意样本；论文报告 F1 0.817、FPR 1.13%、AUPRC 0.830，较两种基线的 0.144/0.162 高约 5–6 倍，LLM 输入 token 较全文件扫描减少 77%，加权平均额外延迟约 818 ms。

### 对 Agent 服务器的采用设计

**工程推断：** 把 Skill 准入做成不可绕过的 `ArtifactAdmission`，键为内容 hash、publisher identity、来源、规则版本和 judge 版本。registry/MCP/Git 下载先进入只读 quarantine；静态规则输出结构化 hit，LLM 只能给风险信号，最终策略由服务器决定。放行生成带作用域与 TTL 的 attestation，运行时 loader 只接受 attested hash；Skill 请求的工具和网络能力另走 capability policy，不能因内容扫描通过自动获权。规则、judge、申诉与撤销都写入可重放审计。

### 验收不变量

- 任意 Skill 在产生 attestation 前不得进入 Agent prompt、资源读取路径或脚本执行器；绕过 proxy 的本地路径必须默认拒绝。
- 改变一个字节、来源、publisher 或规则版本后旧 attestation 无效；已撤销 hash 在缓存节点和长会话中都必须于 SLO 内失效。
- 对编码、拆分、跨文件引用和提示注入变体做对抗回归；线上 FPR、恶意漏报率、P95 准入延迟和 LLM token 成本有独立门槛。
- judge 超时或不可用时，高风险命中必须 fail closed 或进入人工队列，不能因为“审核服务故障”自动放行。
- 即使 Skill 被判良性，其脚本、网络、secret、shell 和写权限仍由独立 capability gate 决定，并与 run/tenant 绑定。

### 边界与风险

威胁模型是假设攻击者不知道部署规则的非自适应对手；公开规则后会面临规避。恶意样本为手工构造，F1 不能等同真实 registry 检出率；LLM judge 自身也可能被 Skill 内容注入。预筛未命中即放行提高效率，但对新型语义攻击有天然盲区。它应作为供应链准入的一层，而非替代签名、publisher 声誉、最小权限、沙箱与运行时行为检测。

## 4. OrchBench: Evaluating Multi-Agent Orchestration Plans in Isolation via Deterministic Simulation

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.25656)
- 首次公开：2026-07-28；作者机构：复旦大学、中关村学院、Queen Mary University of London；类型：机构预印本与跨框架实验；总分：**97/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 端到端多 Agent 评测同时受 planner、worker 模型、工具故障、环境噪声和随机性影响，失败后很难归因于编排；实际执行的 token 与时间成本又阻止团队系统扫描 agent 数、上下文上限、任务规模和 handoff 策略。仅比较最终答案会掩盖丢失依赖信息、过度压缩和无收益并行。

### 原设计

**来源事实：** OrchBench 把真实任务扩展为带依赖、token/time cost 与压缩敏感度的 DAG，规模覆盖 10 到 1,000 个子任务。被测 planner 只输出 agent pool、任务分配和跨 Agent 信息传递/保留率；确定性 simulator 在给定上下文与 agent budget 下计算质量、关键路径 makespan、token、缺失传递和综合分，不调用 worker。模拟结果与 Claude Code 真实执行质量相关系数为 0.816，成本为 1.3% token 和 10.3% wall time，并在 Claude Code、SWE-mini、OpenHands、Crush 四框架维持正相关。实验发现 transfer coverage 与质量的相关性为 0.614–0.952；到 100 个任务时 agent 数与质量近乎无关。模拟筛选后仍要求目标框架实跑；一次 simulator-guided handoff 调整把 20 个任务的真实均分从 3.754 提高到 4.150/5。

### 对 Agent 服务器的采用设计

**工程推断：** 在发布新编排前先编译 `OrchestrationPlan`：显式任务 DAG、agent pool、handoff schema、最小保留字段、context 与 cost budget。离线 deterministic simulator 用固定版本的 task cost/quality 模型扫并发度、故障与上下文压力，产出可解释的缺失依赖和瓶颈；只有通过静态/模拟门的 plan 才进入小规模真实 canary。真实 trace 反向校准参数，但不能用同一批结果同时训练和宣称验证。生产调度器记录计划版本与实际偏差，让“模拟通过、线上失败”可归因。

### 验收不变量

- 相同 DAG、plan、simulator 版本和 seed 必须得到字节一致的指标；模拟器升级要保留旧结果可重放。
- 删除任一必要跨 Agent handoff，simulator 必须显示可定位的 transfer loss；不能只在最终总分中静默下降。
- 对 agent 数、context limit、tool failure 和 deadline 做 sweep；选择的是质量/时延/token 的 Pareto 方案，不能只优化单一综合分。
- 任何计划即使模拟高分，也必须通过目标 runtime 的 canary、真实 effect 幂等和故障恢复测试才能发布。
- 线上观测与模拟预测持续偏离超过阈值时暂停自动扩大发布，并标记对应 cost/quality 模型过期。

### 边界与风险

模拟器将工具等待、worker 推理和部分真实资源限制抽象掉，时间和 token 的模拟—真实相关性也低于质量；DAG 和质量传播规则本身含模型与设计者判断。0.816 是相关而非逐任务等价，且论文使用的是特定任务与 2026 年模型。它适合低成本筛选与诊断，不能替代真实环境的可靠性、安全和业务结果评测。

## 5. Discover Agent Skills from MCP servers in .NET

- 原始来源：[Microsoft Agent Framework 官方工程博客](https://devblogs.microsoft.com/agent-framework/discover-agent-skills-from-mcp-servers-in-net/)；[官方文档](https://learn.microsoft.com/en-us/agent-framework/agents/skills?pivots=programming-language-csharp)；[官方示例](https://github.com/microsoft/agent-framework/tree/main/dotnet/samples/02-agents/AgentSkills/Agent_Step06_McpBasedSkills)
- 首次公开：2026-07-28；类型：官方工程博客、API 文档与可运行示例；总分：**97/100**（来源可信度 25，问题具体性 20，架构深度 23，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 把 Skill 复制进每个 Agent 部署会造成版本分叉和协调重发；远程 MCP 分发可集中更新，却把“受认证连接上的内容”引入本地 prompt 与文件系统。归档可能超大、解压后膨胀、包含过多文件或脚本；服务器内容热更新还可能让同一 run 前后读取不同政策。认证只证明连接端身份，不证明内容安全或适合执行。

### 原设计

**来源事实：** MCP server 通过 `skill://index.json` 广告 Skill，框架支持逐文件 `skill-md` 和 ZIP/TAR/gzip TAR `archive` 两种分发。Agent 起初只看到简短广告，匹配任务后才读取 `SKILL.md` 和资源。归档下载/解压受 `ArchiveMaxSizeBytes`、`ArchiveMaxUncompressedSizeBytes`、`ArchiveMaxFileCount` 和受控目录限制；超限 Skill 跳过。远程 archive 中的脚本永不执行，`load_skill`、`read_skill_resource`、`run_skill_script` 默认需要审批。来源明确说明 MCP Skills API 与规范仍为实验性；文档还警告本地示例 subprocess runner 不具备生产沙箱。

### 对 Agent 服务器的采用设计

**工程推断：** 中央 Skill 服务必须发布不可变 `SkillRelease(name, version, content_hash, manifest, signer)`，index 只做发现，run 在首次选择时钉扎 release。下载器使用无符号路径规范化、逐项与总量限额、压缩比和 deadline，解压到 run-scoped 只读目录；拒绝 symlink、hardlink、绝对路径和 `..`。远程文本先过 ArtifactAdmission，再进入 prompt；脚本与资源分开授权，archive 脚本保持不可执行。热更新只影响新 run 或显式迁移点，审计保留选择、下载、hash、审批和读取记录。

### 验收不变量

- 对 zip slip、symlink/hardlink、重复文件名、压缩炸弹、文件数和 CPU/超时做攻击测试；任何文件不得逃出 run-scoped 根目录或突破资源预算。
- 同一 run 的 Skill hash 必须稳定；服务端 index 更新后，已启动 run 继续使用已钉扎版本，不能在中间 turn 静默换指令。
- 远程 archive 中任何脚本都不可执行；把脚本伪装为资源、改扩展名或在 Markdown 中请求 shell 也不能绕过 capability gate。
- MCP 身份、Skill signer、内容 hash 和租户授权必须同时满足；从另一 issuer 或租户复制 URI/缓存不得成功加载。
- 撤销 release 后，新 run 立即拒绝；活跃 run 按风险策略终止或在明确安全点迁移，并留下完整审计收据。

### 边界与风险

这是实验性 API，文章没有吞吐、缓存一致性、撤销传播或对抗安全基准。体积限制只能阻止资源耗尽的一部分，不能判断自然语言指令是否恶意；“远程脚本不执行”也不能防止指令诱导 Agent 调用已有高权限工具。中央分发减少版本分叉，同时扩大中央 Skill 服务与签名密钥的故障半径，应配合多版本回滚、缓存隔离、内容扫描和最小能力授权。
