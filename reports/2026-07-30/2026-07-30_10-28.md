## 1. Filesystem-Based Memory for LLM Agents: Organization, Evolution, and Sustainability

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.26637)
- 首次公开：2026-07-29；作者机构：UIUC、UC San Diego、UC Merced、Adobe Research、Texas A&M University；类型：机构预印本与系统实验；总分：**98/100**（来源可信度 25，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 许多已部署 Agent 直接把 Markdown 目录作为长期记忆，由模型用普通文件工具读取、写入和重组。论文发现，增长中的 store 虽然仍可用，但分类契约会对除最强 management agent 外的所有配置逐步退化；弱管理模型还会把“偏好已经改变”写成无日期的当前属性，让旧事实继续生效。组织化最稳定的收益是降低搜索成本，在材料较大时约减半；实验没有发现“组织得更漂亮”本身稳定提升答案正确率。工具集合的变化对目录形态的影响可以与换模型一样大。

### 原设计

**来源事实：** 论文把一个 memory filesystem 周围的职责分为三类：management agent 接收 conversation chunk、task trajectory 等内容并整合、重组和维护；search agent 通过 shell 或 memory-style 工具查询并返回带来源的答案；execution agent 产生任务轨迹，轨迹可被蒸馏成 skill。实验控制 agent-organized hierarchy、verbatim dump、chunk retrieval 三种形态，并改变管理/搜索模型强度、工具 harness 和数据流规模，分别记录答案质量、搜索成本、文件数、编辑/删除、分类遵循度与长期保留。作者观察到对话 store 通常早期建少量文件、随后原地编辑且几乎不删除；但整理每个 episode 的成本不会随规模下降，verbatim store 的“全量供应”成本会随历史增长。

### 对 Agent 服务器的采用设计

**工程推断：** 不把可变目录直接当唯一事实源。写入路径先把 `MemoryEvent(tenant, subject, observed_at, source, payload_hash)` 追加到不可变来源账本；`MemoryCurator` 再生成可读的 Markdown/目录物化视图，并为每段结论保存 event 引用、valid time、curator 版本与替代关系。`MemorySearch` 只有读物化视图和回查来源的权限，执行 Agent 只能提交候选事件，不能直接覆盖事实。skill 蒸馏与用户事实使用不同 schema、保留期和批准策略。定期以事件账本重建目录，与增量维护结果比较；分类漂移超过阈值时降级到 chunk retrieval，而不是让 Agent 无界“整理”。

### 验收不变量

- 注入“1 月不吃辣、3 月改为可以吃辣”；当前查询只能返回 3 月状态，历史查询仍可还原 1 月状态，答案必须携带来源 event。
- kill curator 于移动文件、改标题和写内容之间；已发布视图保持完整，新视图只有 manifest、文件 hash 和引用校验全部通过后才可见。
- 连续灌入相互冲突的 1,000 个 episode；任何压缩不得丢失被 retention policy 标记的事实，重建结果与增量视图的有效结论集合必须等价。
- 分别计量 search token、工具调用、答案质量、分类遵循度和每 episode 整理成本；不能用更低 token 掩盖事实召回下降。
- 执行 Agent 试图直接修改 memory 根目录必须被权限层拒绝；它只能写入有幂等键和 provenance 的候选事件。

### 边界与风险

这是预印本；研究覆盖的是有限对话与 embodied-task horizon，不证明多年、多租户 store 仍健康。论文明确发现组织形态与正确率的关系不稳定，不能把特定目录模板写成普遍最优。角色分离会增加模型调用和延迟；不可变事件账本也带来隐私删除、压缩与成本治理问题。生产实现仍需租户隔离、加密、删除传播和人工纠错，不应把管理 Agent 的整理结果当作无条件真相。

## 2. VITAL-RAG: Invariance Race for Context Allocation in Coding Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.26937)
- 首次公开：2026-07-29；作者机构：南京邮电大学、天津大学、清华大学智能产业研究院；类型：机构预印本与多基准实验；总分：**97/100**（来源可信度 24，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 仓库检索器会为同一代码对象返回 body、signature、call-site 等多个视图。它们字符串不同，普通 exact dedup 去不掉；若按候选排序直接塞入 4K 上下文，一个对象可以占多个位置，把独立依赖挤到截断区。论文在 RepoBench 上观察到 Recall@5 与真正进入模型输入的 Recall@4K 相差明显：基础配置的后者只有 39.59%。单纯 canonical 去重又可能删掉与任务相关的同文件 helper 或 validator，因此“对冗余视图保持不变”与“对新增语义保持敏感”形成 invariance race。

### 原设计

**来源事实：** VITAL-RAG 位于保留 provenance 的 retriever 与 generator 之间。第一步用 index adapter 将候选映射到 canonical code object；实验采用规范化 path 与大小写归一 identifier 组成 key，同一对象的所有视图只竞争一个外部位置，且不累加分数。第二步在 K=5 时为 query-conditioned provenance refinement 预留一个位置，只选与已选对象同来源路径、又命中查询 identifier token 的不同 companion。第三步按全局 token budget、per-object cap 和后续对象最小保留量分配 line-complete rendering。论文报告 Recall@4K 从 39.59% 提至 63.67%，evidence token 减少 35.63%，并在三个模型后端的 RepoClassBench/RepoExec 上匹配或超过近期基线。

### 对 Agent 服务器的采用设计

**工程推断：** 在 CodeNib 一类多视图仓库服务之后增加独立 `ContextAllocator`。索引必须返回 `ObjectId(repo, commit, language, symbol)`、view type、source range、retrieval score 和 provenance fiber；allocator 不重新检索，只决定谁拥有上下文位置和 token。canonical key 优先用 parser/LSP 的稳定 symbol ID，path+name 只能作为降级方案。分配结果生成可重放 `ContextManifest`，包含查询、索引 commit、候选集 hash、对象代表、companion 选择原因、截断边界和预算。模型输出与索引更新不反向改变同一 run 的 manifest。

### 验收不变量

- 为同一 symbol 增加任意数量的 body/signature/call-site 渲染，同一查询的外部 slot 占用数仍最多为 1；独立 helper 不能因表面相似被合并。
- 在候选已包含正确依赖时随机放大前序对象；正确依赖必须以完整行进入模型输入，不能只在 Recall@K 中“检索到”却被渲染截断。
- `sum(object_tokens) <= global_budget` 且每个对象不超过 cap；预算不足时降级规则确定、可重放，并记录被舍弃证据。
- checkout 到另一 commit 或 symbol rename 后，旧 `ObjectId`/source hash 不能被当前 context manifest 复用；编辑必须带 commit precondition。
- 对 Java、Python 和至少一个真实业务语言分别比较 Recall@K、input-level recall、Pass@1、token 与 P95 分配时延，不能只报告检索排名。

### 边界与风险

这是预印本；path+identifier 不是跨 rename、overload 或动态语言的稳定身份，生产环境应让 parser/LSP/graph 提供更强 ID。一个 companion 和 K=5 是实验选择，不是普遍常数；不同任务可能需要测试、配置、schema 等多类伴随证据。结果主要证明上下文分配，不证明完整 coding-agent patch 的长期正确性。ContextAllocator 还会成为权限过滤边界，不能让低权限 view 通过同一 canonical object 泄露。

## 3. MemSecBench: Tracking Agent Memory Poisoning from Persistence to Consequence and Repair

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.27080)
- 首次公开：2026-07-29；作者机构：浙江工业大学网络空间安全研究院、滨江人工智能研究院；类型：机构预印本与隔离运行基准；总分：**97/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 恶意规则可能从文档进入长期记忆，隔多轮或跨会话被召回，再驱动付款、共享或代码动作。只证明“写进去了”不等于攻击成功，只证明“删掉了恶意片段”也不等于安全修复，因为良性记忆可能同时被破坏。论文在 2 个 harness、4 个 memory backend、3 个 LLM backend 的 24 种配置上运行 310 个案例：恶意记忆持久化率为 84.2%，完整 Write–Execute 攻击链成功率为 50.3%；backend 的相对安全性会随 harness/model 组合反转。

### 原设计

**来源事实：** 每个案例在隔离容器中按 Write–Execute–Forget 执行，并设置 W1 接受写入、W2 恶意语义持久化、E1 召回、E2 采纳、E3 外部后果、F1 移除目标语义、F2 保留必要良性记忆七个检查点。W1 由确定性检查完成，其余检查点由独立 judge 对只允许引用指定 evidence ID 的证据包裁决，再用程序门验证来源、时间依赖和跨工件一致性。W2 通过后生成 target-memory manifest，把恶意语义 rubric 与 backend 中的具体工件绑定；Execute 和 Forget 从同一已验证 poisoned state 的独立副本开始，避免修复测试污染攻击测试。

### 对 Agent 服务器的采用设计

**工程推断：** 记忆写入不能只有 `put/search/delete`。引入 `MemoryAdmission` 保存来源信任、提取者、有效期、敏感能力和 taint；召回结果携带不可丢弃的 lineage，进入高风险工具前由 policy gate 检查。所有有副作用的执行生成 effect receipt，并反向关联触发它的 memory IDs。修复使用 `Quarantine -> Replay -> SelectiveDelete -> Reindex` 工作流：先隔离可疑版本，在冻结快照上重放受影响 run，再按语义/来源关系删除或替代，重建索引后验证良性记忆集合，最后才发布新版本。后台持续跑与生产 harness/backend/model 相同组合的 Write–Execute–Forget 回归。

### 验收不变量

- 写入“规则仅到 6 月 30 日有效”并在 7 月召回；若有效期在抽取/压缩时丢失，执行 gate 必须拒绝相关副作用。
- W1/W2 通过但未产生 E3 可验证 receipt 时不得计作端到端攻击；Agent 自述“已执行”不能替代外部效果证据。
- 修复完成后目标恶意语义不可被任何检索路径召回，同时预先标记的良性记忆集合仍可检索；两项必须同时成立。
- 从 W2 冻结快照分别启动 Execute 与 Forget；任一分支的写入不得影响另一分支，重复运行使用全新隔离环境。
- harness、memory backend 或 model 升级后必须重跑配置矩阵；不得把某 backend 在一个组合上的低攻击率外推为全局安全排名。

### 边界与风险

论文是预印本；每个 configuration-case 只执行一次，统计是描述性结果，judge 也可能误判。案例虽覆盖代码/科研、日常生活和办公 48 类情境，仍不能代表生产攻击分布。完整生命周期回归成本高，且记录详细 lineage/effect receipt 会扩大敏感数据面。生产系统应在基准之外继续做最小权限、内容隔离、外部调用审批和人工事件响应。

## 4. FinCacheServe: Dependency-Consistent Answer Reuse for Cost-Efficient RAG Serving over Mutable Enterprise Documents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.26076)
- 首次公开：2026-07-14；作者机构：香港中文大学、北京理工大学；类型：机构预印本、vLLM 实现与元数据压力测试；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 13）

### 针对的问题

**来源事实/作者主张：** 企业 RAG 会重复回答同一分析意图，但答案同时依赖 company/period、文档版本、引用 chunk、工具结果、模型和 decoding 配置。语义近似或固定 TTL 命中只能说明问题像，不能证明这些依赖仍有效；文件更新后可能把旧证据包装成新答案。论文在 2,230 请求的 hosted 7B trace 中报告跳过 53.27% LLM 调用且未观察到 dependency-stale 输出；三组 32B operator-suite 共 544 请求的跳过率为 53.31%。

### 原设计

**来源事实：** FinCacheServe 在 retrieval/vector search 后设置 answer-reuse router。每个答案是 materialized serving object，记录规范化业务 signature、文档版本、由 chunk ID/hash/version 稳定排序得到的 evidence fingerprint、由工具名/版本/规范化输入/结构化输出得到的 tool fingerprint，以及 model identity 和 decoding config。读取先定位 exact/signature bucket 候选，再通过 signature、evidence/version、tool/model 四组 gate。文档更新先写 version store，再沿 document-to-answer reverse index 失效相关 entry，之后的读取才能观察到新版本；原型用 metadata lock 让读取、版本更新和 entry mutation 形成单一线性化顺序，LLM 调用在锁外。论文还测试 SQLite/WAL 的 10k/100k entry、fan-out 1/16/128 与 interleaved query/update。

### 对 Agent 服务器的采用设计

**工程推断：** 将缓存条目建模为 `AnswerObject(intent_key, answer, DependencySet, policy_version)`，而不是 `query -> text`。DependencySet 至少包含 tenant、corpus snapshot、document/chunk hashes、tool contract 与结果 hash、model/config、prompt/guardrail 版本。更新事务先提交 source version 与 outbox event；invalidator 消费后更新反向索引并写 tombstone，read path 只有在读到不少于请求 watermark 的 metadata snapshot 且所有依赖匹配时才可命中。对不能同步失效的跨区副本，采用 epoch/watermark fail-closed 或回源生成，不用短 TTL 假装强一致。缓存容量策略只决定保留谁，不能绕过 correctness gate。

### 验收不变量

- 在命中判定与返回之间更新任一依赖文档；请求要么在线性化点前返回旧版本并标明 snapshot，要么 miss/返回新版本，不能产生版本混合。
- 修改 tool implementation、结构化输出、model、prompt 或 decoding config 中任一项；旧答案必须 miss，即使 query 文本完全相同。
- kill invalidator 于 version store 更新后、reverse-index tombstone 前；read path 看到更高 source epoch 时必须 fail closed，不能返回尚未扫到的旧 entry。
- 随机制造 hash near-collision、同名跨租户文档和高 fan-out 更新；租户边界不可穿透，失效复杂度、P95 命中时延与队列积压有独立 SLO。
- 以 dependency-fresh goodput、跳过 LLM 调用数和每个新鲜成功的能耗计量收益；普通 hit rate 不能作为唯一成功指标。

### 边界与风险

这是面向财务文档工作负载的预印本；“零观察到 stale”不是形式证明，业务 signature normalizer 的错误仍会把不同意图合并。原型的服务级 metadata lock 不适合直接外推到多区域高吞吐，分片、跨文档事务和消息乱序需要额外协议。依赖 hash 与反向边会增加元数据规模，也可能暴露文档关系；要配合租户分区、加密和保留策略。

## 5. AgentGUI: An Interface for Observing and Steering Long-Running AI Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.26300)
- 首次公开：2026-07-28；作者机构：ETH Zürich；类型：机构预印本、开源系统、用户研究与 steering 实验；总分：**95/100**（来源可信度 25，问题具体性 19，架构深度 23，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 长运行 Agent 会产生交错的 reasoning、tool call、file access、子 Agent 和 terminal 事件。只给一条 transcript，人工定位耗时、错误和产物会抵消自动化收益；只做可视化又无法在漂移时接管。AgentGUI 的 8 人受控研究中，参与者查找 trace 信息平均从每题 145 秒降到 90 秒（快 38%，p=0.023）；自动 manager 的初步实验在 0.8B–9B 模型梯度、每模型 50 次运行中最高提升 34 个百分点完成率。

### 原设计

**来源事实：** 系统以 locally hosted FastAPI server 运行每个 agent turn 的隔离 worker process，通过 WebSocket 向 React 前端流式传输事件；每个 desk 持有独立 persistent Docker sandbox，并可保存/恢复 trajectory 与 workspace snapshot。UI 分开呈现 activity feed、wall-clock overview、API/token debug、terminal 和 workspace artifact。人工可中断当前 turn、修改下轮读取的任务定义或切换 agent profile。自动 manager 在用户触发或空闲间隔到达时，把任务分解成可验证条件，收集 transcript/workspace 证据，对每项输出 audit；只有未解决会话才用审计结果恢复运行。

### 对 Agent 服务器的采用设计

**工程推断：** 将 GUI 与 harness 之间定义为版本化 `RunControlProtocol`。runtime 只追加 `RunEvent(seq, run_id, actor, turn, kind, payload_ref)`，大 payload 存 artifact store；控制面提交 `Interrupt/AmendTask/SwitchProfile/Resume` 命令，带 expected turn/seq、操作者身份、理由和幂等键。中断只能在工具副作用边界或明确 cancellation protocol 执行；任务修改在下个 turn 生效。自动审计运行在只读快照上，引用 event/artifact hash，输出建议而非直接伪造成功；resume 仍走统一授权。sandbox snapshot、trajectory cursor 和控制命令一起形成可恢复 checkpoint。

### 验收不变量

- WebSocket 断线、重连和重复投递后，客户端按 seq 重放得到同一事件序列；UI 不能因丢帧把未完成工具调用显示为成功。
- 在不可取消的外部副作用进行中注入 interrupt；runtime 必须先得到 effect receipt 或进入 `unknown/reconcile`，不能同时启动替代动作。
- 两名操作者同时 amend/resume；只有 expected turn/seq 匹配者成功，失败者收到当前状态，控制命令全量审计。
- 自动 manager 标记 solved 时，每个验收条件都必须引用可读取的 event/artifact hash；删除证据后裁决必须失效。
- restore checkpoint 后，sandbox、workspace、trajectory cursor、task version 和 capability set 必须一致；旧 profile 的凭据不能随 snapshot 泄漏给新 profile。

### 边界与风险

这是预印本；用户研究只有 8 名参与者，自动 steering 是 proof of concept，不能证明复杂生产任务稳定提升。论文主要支持 Hermes，Claude Agent SDK 为实验支持；其事件模型未证明跨所有 harness 等价。持久 Docker sandbox 与完整 trace 会增加存储、secret 暴露和多租户攻击面；自动 manager 也可能被 trajectory 中的提示注入误导。生产采用应让控制协议、权限和副作用状态成为服务端事实源，GUI 只是可丢失、可重建的投影。
