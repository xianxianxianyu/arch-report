## 1. SIGIL: Compiling Agent Skills into Typed Harnesses

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.27309)
- 首次公开：2026-07-29；作者机构：University of Michigan；类型：机构预印本与 30-Skill 实验；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 当前 Skill 通常是加载进上下文的自然语言流程。模型每次运行都重新解释控制流、工具绑定和停止条件，因此可以正确复述规则，却不执行规则。论文观察到三类典型失败：声称测试通过但没有重新运行命令；描述将调用 GitHub API 但实际没有发出请求；把需要逐段审批和提交的流程压成一份最终文档。输出级测试仍可能接受这些看似合理的工件，因为错误发生在过程而非最终文本。30 个 Skill 上，prose agent 只执行 56% 的强制步骤；换一代模型后升到 68%，仍没有形成保证。

### 原设计

**来源事实：** SIGIL 把 Skill 编译为可执行 harness。第一阶段从 Markdown 提取类型化 `AG-IR`：每个节点都声明 owner（代码或模型）、modality（mandatory、forbidden、discretionary 等）并保存支持它的原文引用。提取结果必须通过来源支持、一致性和有效性 compile gate；第二阶段用固定规则确定性 lowering 到 Jac/Object-Spatial Programming runtime，不再引入模型判断。mandatory 步骤变成进入节点即执行的代码能力，forbidden 操作变成根本不存在的路径，discretionary 判断变成供周围代码消费的类型化 verdict。命令是否运行、退出码和失败数由代码写入 evidence object，模型不能自行填成“成功”。编译后强制步骤执行率为 86%，完整流程完成率是 prose 的 2.3 倍，token 使用约为 0.58 倍；86% 在两代模型间保持稳定。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 将 Skill 发布拆成 `Source -> ExtractedIR -> ValidatedIR -> RuntimeArtifact` 四个不可变版本。IR 节点至少包含 `node_id`、owner、modality、输入/输出类型、tool capability、幂等键策略和 `source_span_hash`。模型只能负责分类、生成、评审等开放节点；读取权威状态、执行命令、审批、写文件、发送请求和验证收据默认是代码节点。编译产物生成 manifest，绑定 Skill hash、编译器版本、工具 contract 版本和策略版本；运行时只加载已签名产物，不能在单次 run 内重新解释原 Markdown。Skill 更新必须重新编译、做 IR diff，并在影子环境回放旧用例。

### 验收不变量

- 删除 Skill 中一条强制检查的来源句后，旧编译产物仍可重放，但新版本必须无法沿用该节点的来源证明；未经重新审批不得发布。
- 让模型输出“测试已通过”但不给验证节点任何真实命令收据；成功状态必须不可达，最终工件即使内容正确也不能标记为 compliant。
- kill runtime 于副作用节点完成、receipt 写入前；重试必须使用同一幂等键查询或对账，不能盲目重复外部动作。
- 任一 runtime 节点都能追溯到 Skill 版本和 source span；任一 mandatory 节点缺少 trace event 时，整个流程的程序合规率为失败。
- 编译器或 tool schema 升级后，对固定 Skill 集比较 IR diff、mandatory coverage、完整流程完成率、token 和 P95 时延；不能只比较最终文本质量。

### 边界与风险

这是预印本，实验只有 30 个 Skill、两代模型，且实现依赖 Jac/OSP。提取阶段仍使用模型；“有原文引用”只能证明编译节点来自文档，不能证明文档本身安全或业务正确。开放式判断无法全部编成确定性代码，论文报告的 86% 也不是 100%。生产采用还需处理 compiler compromise、工具 schema 漂移、Skill 供应链签名、秘密隔离和旧运行兼容，不能把编译器输出直接视为可信程序。

## 2. MemTxn: A Transaction Boundary for Source-Supported Updates and Complete-State Recovery in Agent Memory

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.27834)
- 首次公开：2026-07-30；作者机构：Beijing Normal University；类型：机构预印本、记忆问答实验与持久故障注入；总分：**99/100**（来源可信度 24，问题具体性 20，架构深度 25，证据强度 15，Agent 服务端价值 15）

### 针对的问题

**来源事实/作者主张：** 可写长期记忆不仅要“检索相关”，还要决定某个候选值是否有来源支持、冲突版本谁可见，以及故障后应恢复哪个应用状态。文本重叠检查会把“不是 30 天退货期”错误写成“30 天退货期”；存储层原子写只能保证物理记录全有或全无，无法知道版本指针、事实键、事件和当前可见集合组成的语义 preimage。只撤销一个观测到的坏键，数据库重开后仍可能留下新旧混合状态。

### 原设计

**来源事实：** MemTxn 位于 answer model 外部，包含三部分：`Ordered PatchTest` 在 commit 前检查候选更新是否按顺序受来源片段支持；`Temporal Resolver` 按明确的时间契约选择冲突事实的当前可见版本；durable snapshot journal 保存更新前的完整 active map，并在检测到不变量失败时恢复整个应用可见 preimage。held-out 审计中，论文报告接受全部 60 个受支持原值并拒绝 179 个由否定、替换和重排生成的 hard negatives；在 LongMemEval-S 与 LoCoMo 的持久多键故障中，系统不需要知道实际物理 write set 也能恢复声明的完整 active map。MemoryAgentBench 的代表设置中，相比 Dense 检索 F1 提升 17.06—24.07 个百分点。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 把 memory write 建模为 `MemoryTxn(tenant, subject, source_event, candidate_patch, expected_memory_version, valid_time, idempotency_key)`。准入器先验证来源 span、主体和策略，再把 preimage manifest、candidate、resolver 版本写入事务日志；提交阶段只发布新的 `visible_state_version` 指针。answer path 只读取单一已提交版本，不直接拼接所有相似事实。恢复器按 manifest 校验完整 active map、版本指针、事实对象和派生索引；任何一项不一致都保持旧版本可见并隔离候选版本。物理数据库事务仍负责原子性，MemTxn 层负责语义准入和应用状态恢复，两层不能混为一谈。

### 验收不变量

- 注入原文“政策不是 30 天”与候选“政策是 30 天”；即使词集合完全重叠也必须在 commit 前拒绝，拒绝不得改变当前可见版本。
- kill 进程于事实对象、版本指针、事件日志、向量索引分别写完的四个位置；重启后只能看见完整旧版本或完整新版本，不能出现混合 active map。
- 并发提交两个冲突事实时，只有 expected version 匹配者能提交；失败者必须重新解析，不得以 last-write-wins 绕过时间契约。
- rollback 后关闭并重开数据库两次；visible facts、版本指针、事件重放结果和派生检索结果必须等价于同一个 preimage manifest。
- 跨租户复制同名 subject 和相似来源；事务、journal、resolver 与索引失效都必须按 tenant 分区，不能让语义相似度跨过授权边界。

### 边界与风险

这是预印本。Ordered PatchTest 证明的是受控的有序词法支持，不证明语义角色、来源真实性或业务真值；179 个 hard negatives 是模板构造。论文没有覆盖并发/重复故障、自然触发分布、意图污染和物理介质丢失。完整 active-map preimage 还会放大写成本与隐私数据面。生产系统仍需 consent、retention、encryption、删除传播、访问控制和日志最小化，并应把大状态快照实现为内容寻址 manifest 与增量对象，而不是复制整个租户数据库。

## 3. MANTA: Multi-Agent Network Topology Adaptation for Self-Evolving Multi-Agent Systems

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.28527)
- 首次公开：2026-07-30；作者机构：Cornell University、UIUC、Academia Sinica；类型：机构预印本、五基准对照与消融；总分：**98/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 多 Agent 通常在运行前固定角色、边和执行顺序，但中途 trace 可能暴露新的结构性故障：一个 worker 同时承担多个维度并遇到未验证工具失败、多个分支重复执行状态变更、验证发生在副作用之后，或关键证据对 verifier 不可见。固定 topology 无法针对当前任务修复；若让模型无限重建团队，又会造成成本失控、循环、权限扩张和不可复现。

### 原设计

**来源事实：** MANTA 将目标 Agent 系统和 orchestration layer 分开。Planner 根据任务与历史 playbook 生成带角色、嵌套 group、通信边和 visibility policy 的 topology；确定性代码检查 membership、cycle、role、引用和 Agent budget。每个 turn 通过结构化 relay packet 传递答案、证据、置信度和未解决问题，append-only evidence ledger 汇集分支证据。Trace Auditor 只从结构化 trace 标记过程异常，不查看 benchmark 正确答案；Controller 可结束运行，或允许**一次**最多三个操作的 topology mutation，例如扩展 overloaded branch、增加 verifier、改边、改执行顺序或可见性。mutation 先应用到副本并重新验证，随后只再执行一个 final turn。短期 playbook 保存本 run 的 topology/audit/repair，长期 playbook 只从过程信号提炼跨 run 经验。五个 benchmark、每个 30 题、三次运行中，论文报告平均 74.0，领先最强基线 5.8 个百分点；移除 planner 或 mutation 均明显下降。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 将 topology 当成版本化控制面对象 `TopologySpec(version, agents, groups, edges, visibility, capabilities, budgets)`，而不是提示词片段。Planner 只能提交 `TopologyPatch`；独立 validator 检查 DAG、Agent 数、模型/token/时间预算、capability 非扩张、tenant 边界和副作用串行化，成功后生成新版本。执行面按冻结版本路由消息和工具调用；同一个 turn 内不热改图。Auditor 只读 event/evidence snapshot，输出带 event IDs 的 process finding；Controller 根据固定 repair budget 决定是否应用一次 patch。任何 topology 变化都不能自动扩大凭据、网络或数据可见范围。

### 验收不变量

- Planner 提交 cycle、悬空 agent、越过 agent budget 或扩大 capability 的 patch；validator 必须拒绝，旧 topology 继续运行且无部分更新。
- 两个分支生成相同的状态变更工具调用；执行层按业务幂等键合并或串行化，不能因为 topology rewiring 重复产生副作用。
- mutation 前后的 visibility policy 做差集；新 Agent 只能读取完成任务所需的最小证据，旧分支中的 secret 不得随 summary 泄漏。
- Auditor 无法为异常引用 trace/evidence IDs 时不得触发修复；benchmark 分数、人工答案和隐藏测试不能进入运行 playbook。
- 强制 Auditor 连续建议修复；单 run 最多提交一次 mutation 和一个 final turn，超限进入 `needs_human/retry_later`，不能无限自我扩张。

### 边界与风险

这是预印本；每个 benchmark 只有 30 题，主实验使用一个 31B backbone，不能证明动态 topology 普遍优于简单 orchestrator。Auditor 判断的是过程异常而非答案正确，错误 flag 会增加大量 token，漏报则维持坏拓扑。长期 playbook 还可能积累任务数据、错误经验或提示注入。生产采用应先把 mutation 限制为少量可审计 operator，并证明单 Agent/固定 workflow 不够用；不要一开始就让模型自由创建任意 Agent 网络。

## 4. AgentRadio: Passive Awareness for Long-Horizon Multi-Agent Collaboration

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.28430)；[代码仓库](https://github.com/Coral-Protocol/AgentRadio)
- 首次公开：2026-07-30；作者机构：Coral AI Labs、University of Luxembourg、King's College London、University of Hull；类型：机构预印本、开源实现与配对实验；总分：**97/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 长时间代码库理解任务可以分工，但各子问题相互依赖：某 Agent 中途发现的配置开关可能改变另一 Agent 的验证方案。阶段式 handoff 或同步 round 只能在边界交换信息，blocking receive 又迫使 Agent 停止当前工作。结果是关键发现留在私人 trace，最终 review 在缺证据时形成一致但错误的结论。

### 原设计

**来源事实：** AgentRadio 提供三种 primitive：thread、message 和 wait-for-mention。独立 message server 保存团队 thread、消息与 mention；每个 coding agent 通过薄 shell 脚本访问。每个 Agent 保持一个后台 watcher 等待 mention，消息只在 foreground work 的下一 step boundary 浮现，不中断正在运行的命令；发送为非阻塞。四个 Agent 按探索、协商分工、执行、交叉审阅和提交五阶段工作。SWE-Atlas QnA 的 124 个任务、1,306 个 rubric 上，单 Agent 的任务准确率为 32.3%，加入分工、协商和 passive awareness 后为 62.1%；开放模型上从 29.0% 到 50.8%。同等花费的六次独立单 Agent best-of-six 只有 37.9%/31.4%，但完整四 Agent 方案平均每题成本约为单 Agent 的六倍。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 把本地 message server 扩展为 durable `TeamChannel`：消息包含 tenant、run、thread、sender、recipient/mention、monotonic sequence、payload/artifact refs、source trust 与过期时间。每个 Agent 保存消费 cursor，watcher 只把已授权、未过期消息排入下一次 model-step 的 inbox；正在执行的工具调用不可被自然语言消息异步打断。大证据进入 artifact store，消息只传 hash 与摘要。队列设置每 Agent/每 thread 配额、优先级和 compaction；协调消息与工具结果使用不同 trust label，不能因为“来自同伴”就升级为指令。

### 验收不变量

- 重复投递、断线重连和 watcher 重启后，Agent 按 sequence/cursor 恰好处理一次语义消息；底层至少一次投递不能造成重复外部动作。
- 在不可取消工具调用中发送高优先级 mention；消息只能在 effect receipt 或 `unknown/reconcile` 状态形成后进入下一 step。
- 恶意 Agent 向无权访问的 thread 发送 artifact 引用；服务端必须在发送与读取两端都做授权，摘要不能泄漏原 artifact。
- 连续灌入 10,000 条低价值消息；有用工作保持 P95 step latency SLO，队列触发背压/compaction，context budget 不得被消息无限占用。
- 对单 Agent、等预算独立并行、blocking negotiation、passive awareness 分别比较成功率、成本、wall time、消息净收益和错误传播，不能只报告最佳最终准确率。

### 边界与风险

这是预印本，评估集中在代码库问答。完整方案成本约为单 Agent 六倍，而且消息也会带来负收益：论文的 passive 层增加 47 个 rubric、同时丢失 23 个。它只能传播已经被某个 Agent 发现的事实，无法修复所有 Agent 都持有的错误概念。生产实现还需解决消息保留、租户隔离、提示注入、队列公平、死成员检测和共享 sandbox 竞争；“异步通信”不应被实现为随时打断副作用执行。

## 5. Hybrid Analysis for Secure MCP Tool Use in LLM Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.25297)
- 首次公开：2026-07-28；作者机构：Zhejiang University、Alibaba Group；类型：机构预印本、sandbox/eBPF 原型与 MCP 安全实验；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** MCP host 看到的是 tool name、schema、参数和返回文本，但本地或受控 MCP Server 的实现还可以启动子进程、访问文件、连接网络。恶意工具可以让声明与返回值都看似正常，实际执行额外副作用；只检查 prompt、description 或 result 看不到这种 tool-execution hijacking。传统 sandbox 能限制资源，却不知道某次文件/网络行为是否与当前用户任务和工具声明一致。

### 原设计

**来源事实：** MTGuard 作为目标 Agent 外部的 guard，覆盖 MCP 调用三个阶段。前置 Parameter Auditor 收集用户任务、历史、tool name、schema 与参数，先跑确定性代码策略、再跑自然语言策略；它刻意排除可能被投毒的自由文本 tool description。Behavioral Monitor 将工具放在 Docker sandbox 中，用 host-side eBPF 与 cgroup v2 归因 process、file、TCP 和 DNS 事件，构造以具体 MCP invocation 为根的 tool behavior tree。后置 Result Verifier 把声明参数、返回值与简化后的执行树一起检查，若违规则不给 Agent 返回结果。99 个攻击案例、三种模型配置中，论文报告平均检出 48.3% 的 unsafe tool calls，基线为 8.3%；平均 false-positive rate 为 3.7%，额外总延迟约 10 秒。作者明确指出：后置拒绝可以阻止坏结果继续影响 Agent，但不能自动撤销已经发生的副作用。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 在 MCP Client 与本地 Server 进程之间放置 `ToolExecutionGateway`，为每次调用生成 call ID、冻结 schema/version、下发最小 capability sandbox，并把声明、策略版本、cgroup、事件树和 effect receipt 绑定成一个审计对象。前置策略负责绝不能发生的动作；高风险写操作进入 staged workspace 或事务性代理，后置验证通过后才 commit。低风险只读调用可直接返回。远程 MCP Server 无法依靠本机 eBPF观测，必须改用远端 attestation、受控 egress proxy、下游 API receipt 或把高风险能力移到自有执行器，不能伪装成同等保障。

### 验收不变量

- 注册“读取公开报告”的工具，实际尝试读取 secret 并外联；即使返回文本正常，event tree 必须关联到同一 call ID 并拒绝结果，sandbox 阻止真实 secret/egress。
- 预启动长驻 MCP worker 后再调用工具；monitor 必须通过 cgroup 捕获既有进程及其后代，不能只跟踪调用后 fork 的进程。
- 在工具返回和 post-verdict 之间 kill guard；高风险 staged effect 保持未提交，恢复后可依据 call ID 重验或回滚，不能默认成功。
- 并发两个调用产生相似文件事件；事件归因不能跨 call 污染，否则 verdict 必须 fail closed 并记录 attribution failure。
- 对每类工具单独度量 unsafe-call recall、false positive、P95 审计时延、trace 截断率和不可撤销 effect 数；平均检出率不能掩盖高风险类别漏报。

### 边界与风险

这是预印本；PDF 带未来会议样式与占位 DOI，不能据此称为正式接收。威胁模型假设每个案例只有一个攻击面被攻破，且 guard、kernel 和监控基础设施可信；串谋、内核逃逸和 guard compromise 不在范围内。当前实现只记录文件名而非完整重建路径，event simplification 与 prompt 截断也可能藏掉攻击。48.3% 检出仍意味着大量漏报，约 10 秒额外延迟不适合所有交互式调用。最重要的是，post-verifier 不是回滚机制；有真实副作用的工具必须先隔离/暂存，再验证后提交。

## 取舍、剩余库存与拒绝项

本轮 5 篇覆盖 Skill 程序合规、长期记忆事务、动态多 Agent 拓扑、异步协作和 MCP 工具执行安全 5 类生产问题；来源分别为 University of Michigan、Beijing Normal University、Cornell/UIUC/Academia Sinica、Coral AI Labs 与欧洲高校、Zhejiang University/Alibaba，没有单一机构超过 2 篇。

验证后预计剩余 10 个合格未发布候选：

- **FAVA**（99）：把自然语言权限降为 evidence-backed permission graph，再由 SMT authorizer 和 runtime gateway 执行；本轮已选择更 MCP-specific 的 MTGuard。
- **HALO**（98）：用 localized obligation 与 dispatch-time recheck 处理 generation-to-action support drift，保留给动作准入专题。
- **AskChem**（98）：2.4M provenance-carrying claims、evidence graph 与 MCP/REST/SDK 接入，领域价值很强，但本轮优先跨领域 runtime 机制。
- **ChronoMem**（98）：全局 memory snapshot 与自然语言语义 rollback；与 MemTxn 同属记忆恢复，后者还覆盖写入准入和 crash recovery。
- **AgentS4D**（97）：6,560 次完整 harness/model 运行揭示“unsafe yet complete”；与上一轮 MemSecBench 的生命周期安全专题接近。
- **Scaling LLM-Driven Multi-Agent Systems**（97）：中等复杂度优于最大 topology，且一致性低于 50%；与本轮 MANTA/AgentRadio 的多 Agent 主题重叠。
- **SafeFlow**（96）：collaboration graph 上的 semantic taint，继续保留给跨 Agent 信息流专题。
- **MRCoder**（95）：draft-model Map/Reduce 仓库上下文选择，与前一轮 VITAL-RAG/CodeNib 主题接近。
- **How to test agent experience changes without shipping them**（95）：真实 URL 拦截和可重复响应变体验证，继续保留给发布评测专题。
- **How to test agent skills without hitting real APIs**（91）：seed/reset 与 HTTP 仿真避免评测污染生产 API，继续保留。

本轮拒绝 4 篇：

- **MemHarness**（81）：主要贡献是 GRPO 训练下的记忆重构策略，架构深度 16、Agent 服务端价值 9，落在硬门槛以下。
- **MIND**（87）：有高质量记忆投毒实验，但核心是 intent-aware learned detector；没有写入准入、lineage、隔离和修复架构，架构深度 17、服务端价值 11。
- **Harness-G**（87）：主要重构 RL 搜索 Agent 的 policy-environment/credit-assignment 接口，服务端状态、恢复和部署边界不足。
- **ORCA-bench**（87）：1,079 个生产拟真 oncall 任务和 50GB telemetry 很有价值，但它是 benchmark，不是 Agent server 设计，架构深度未达门槛。
