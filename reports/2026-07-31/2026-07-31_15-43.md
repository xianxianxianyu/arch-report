## 1. Skill Use or Skill Theater? Evaluating the Reasoning Backroom in Skill-Augmented Language Agents

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.27484)
- 首次公开：2026-07-29；作者机构：University of Liverpool、University of Leeds、MBZUAI；类型：机构预印本、配对干预实验；总分：**99/100**（来源可信度 25，问题具体性 20，架构深度 25，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 评测器通常把推理文本里的 Skill 名称、Agent 自报的“我使用了某 Skill”，或最终准确率当成 Skill 有用的证据，但这些都不能回答“删除该 Skill 后，本次决定会不会改变”。论文称这种可观察叙事与干预测得影响之间的缺口为 Reasoning Backroom：Agent 可能默默吸收 Skill 却不归因，也可能高置信引用一个对决定没有作用的 Skill。净准确率还会把向正确答案和向错误答案的 flips 相互抵消，多 Agent 通信则可能保留影响却丢失原始 Skill/来源。

### 原设计

**来源事实：** Backtrace 先让系统提交答案，再单独询问归因，避免归因请求改变待测决定；每个有 Skill 运行都与同实例、同系统配置的 no-skill 运行配对。测试条件分别删除 Skill、保持语义改写措辞、注入误导规则、交换名称、交换内容和提供无关 Skill，从而区分 displayed identity 与 procedural content。框架记录 decision reliance、signed utility、claimed attribution 和 Attribution Fidelity Score；多 Agent 版本再做成员/来源移除反事实。BackroomBench 覆盖逻辑和竞赛数学、12 个模型变体以及单/多 Agent 配置。数学域没有任何 model-condition 组合超过 0.43 AFS；在 3,600 个逻辑运行上，自报、文本提及、trace 相似度和 LLM judge 的依赖识别 F1 分别只有 0.47、0.13、0.37、0.43，说明单条可见轨迹不能替代干预。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 在 Skill 发布评测中生成不可变 `EvalPair`：绑定 task fixture、model/harness/tool 版本、random seed、skill artifact hash 与一份 no-skill 或 placebo 条件。先冻结 answer/effect receipts，再开独立 attribution phase。聚合器同时保存 `decision_changed`、`effect_delta`、`signed_utility`、`claimed_skill`、`actual_artifact_hash` 和成本/时延，禁止把它们压成一个“Skill 得分”。对多 Agent run，消息携带 `source_skill_hash` 与传播链；需要高可信归因时做受限的 skill-removal、agent-removal 或 content/name swap 重放。发布门以任务族上的净收益、伤害上限和不确定区间判断，不能以“Agent 说用了”判断。

### 验收不变量

- 对同一 fixture 交换 Skill 名称但保持正文，若行为效应保持、归因随名称漂移，系统必须标记 provenance mismatch，不能仍记为可信采用。
- 一个 Skill 造成 20 次正向 flip 和 20 次负向 flip 时，净收益可为零，但 churn、harm rate 与受影响实例必须完整保留，不能显示成“无影响”。
- attribution 请求只能在答案、工具效果和工件 hash 提交后发出；改变 attribution prompt 不得改变已冻结决定。
- 多 Agent 中删除宣称贡献最大的成员后决定不变，而删除未被归因成员后决定变化，必须产生 contribution mismatch 事件。
- 任一 counterfactual pair 的 model、harness、工具版本、预算和环境 manifest 不一致时，pair verdict 必须作废而不是进入发布统计。

### 边界与风险

这是预印本。answer-level intervention 只能证明外部 Skill 与输出决定的反事实关系，不能恢复模型内部机制，也不能排除模型参数中已有等价程序。实验限于冻结文本 Skill、两个推理域、选定系统和多数确定性运行；生产工具任务还要控制外部状态与随机性。反事实运行会近似倍增成本，并可能因环境漂移制造假差异，因此应先用于高价值 Skill 和回归样本，而不是无条件复制所有流量。

## 2. SkillCoach: Self-Evolving Rubrics for Evaluating and Enhancing Agentic Skill-Use

- 原始来源：[arXiv 论文](https://arxiv.org/abs/2607.01874)
- 首次公开：2026-07-02；作者机构：HKUST(GZ)、JD.COM；类型：机构预印本、真实轨迹 rubric 实验；总分：**98/100**（来源可信度 24，问题具体性 20，架构深度 25，证据强度 15，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** outcome verifier 只能告诉我们最终工件是否通过，无法判断 Agent 是否选对 Skill、执行关键步骤、按依赖顺序组合多个 Skill、或在提交前完成验证。Agent 可以靠试错偶然通过，同时读取 distractor、跳过脚本或漏掉检查；若把所有最终通过轨迹都当作好样本，评测和后续训练都会奖励不可复用的过程。共享 Skill 库中的相似候选进一步把瓶颈从“有没有有用 Skill”变成“能否稳定找到并正确使用”。

### 原设计

**来源事实：** SkillCoach 保留独立的最终 verifier，并为轨迹建立四维过程 rubric：selection 用 gold/distractor 集合 F1 与无适用 Skill 时的 abstention；following 要求关键步骤有可见 event evidence；composition 检查先后依赖及中间工件传递；reflection 检查提交前验证。初始 rubric 从任务、gold/distractor Skill、oracle、verifier 信息和真实 rollout 生成；judge 抽取 Skill 读取、工具调用、文件编辑、脚本、工件和验证事件，arbitrator 只提出局部 patch，patch 通过 held-out validation gate 才升级版本。50 个配对审计中，gold-keypoint coverage 从 71.56 升至 83.70，trajectory-filtering consistency 从 82 升至 96，hallucination rate 从 2 降至 0。论文还报告强模型加入 distractor 后 selection 明显下降，并给出约 45—195 个 distractor 即开始退化的模型相关边界。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 将评测拆为 `OutcomeContract` 与 `ProcessContract`。每条 Process check 有稳定 ID、维度、适用条件、pass/fail/skip、所需 event types、证据查询和来源 Skill span；judge 只能针对已有 trace/artifact receipt 给 verdict。Rubric patch 进入 `candidate`，在校准集和 held-out 集上同时比较覆盖、误判、judge 一致性与 skip 密度，达门槛后生成新 `rubric_version`；旧分数不得与新版本直接拼接。Skill 检索层另外做 library-size 和 hard-negative sweep，用退化边界决定预过滤、rerank 与上下文预算，不能把整个注册表直接塞给模型。

### 验收不变量

- Agent 输出正确文件但未运行 Skill 声明的验证脚本；outcome 可以通过，following/reflection 必须失败，两个信号不得互相覆盖。
- judge 给出 pass 时必须引用同 run 的 event/artifact IDs；只引用 Agent 自述“已执行”的 verdict 必须拒绝。
- 新 rubric patch 若提高覆盖却引入任何无来源路径、错误输出格式或不适用硬要求，validation gate 必须拒绝并保留旧版本。
- 对同一轨迹重复 judge 至少五次并与人工校准样本比较；相同输入出现 verdict flip 超过阈值时，相关检查不得进入发布门。
- 从 gold-only 到相似 distractor 逐级扩库；达到 selection degradation boundary 前必须触发检索/重排优化，达到 collapse boundary 必须停止直接模型选择。

### 边界与风险

这是预印本。rubric 质量验证依赖独立 LLM judge 和 human-gold reference，不等于新的大规模人工标注研究；任务也只覆盖筛选后的 skill-dependent workflow。自进化 rubric 仍可能学会迎合现有轨迹或 verifier，validation 集重复使用会过拟合。生产采用应限制 patch operator、保留人工校准金标，并把安全/权限强制项落为确定性代码，而不是交给 rubric judge 决定。

## 3. Dynamic Agent Skills: A Lifecycle Survey and Taxonomy of Evolving Skill Libraries

- 原始来源：[arXiv 记录](https://arxiv.org/abs/2607.10113)；[OpenReview 记录](https://openreview.net/forum?id=cjU3YbcRr8)
- 首次公开：2026-07-11；作者机构：Carnegie Mellon University；arXiv 记录注明 2026-07 被 TMLR 接收；类型：124 篇材料的生命周期综述；总分：**97/100**（来源可信度 25，问题具体性 19，架构深度 25，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 动态 Skill 库不是静态提示词集合，而是会改变未来检索、组合、执行和信任判断的持久状态。只做 `Add/Refine` 会形成单调膨胀：相似 distractor 增多、旧 Skill 漂移、错误更新扩散；“被读取/被调用”也不等于带来下游收益。许多 benchmark 只看期末成功率，隐藏 Skill inflation、incorrect-skill drift、maintenance-off collapse、检索退化和 usage–utility gap。

### 原设计

**来源事实：** 文章把静态 Skill 的 applicability、policy、termination、interface 扩成七字段记录，再加入 edit、verification 和 lineage；库状态以 `L_t -> L_t+1` 表示，由 Add、Refine、Merge、Split、Prune、Distill、Abstract、Compose、Rewrite、Rerank 十类 operator 驱动。八阶段生命周期包括 evidence、proposal、verification/admission、storage、retrieval/composition、maintenance、distillation/portability 和 governance。最关键边界是 candidate 与 admitted state：候选可先 tentative/quarantined，再 promotion、demotion 或 rollback。综述区分 execution test、LLM rubric、ensemble、symbolic graph、rollback、utility 和 security triage 等 verifier 的时机、覆盖与成本，并强调大库中 retrieval、storage topology、pruning 和 provenance 实际上是一个系统。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 建立版本化 `SkillRegistry`：`SkillCandidate` 保存 base version、operator、来源 evidence、作者、依赖和候选工件；`AdmissionDecision` 保存 verifier bundle、各门 verdict、rubric/environment 版本和风险级；只有原子提交后才生成 `AdmittedSkill(version, maturity, lineage, compatibility, capability)`。检索默认只见 admitted 且与租户/任务授权匹配的版本；trial Skill 只进 shadow 或小流量 cohort。运行时记录 usage receipt 与 counterfactual/业务 effect receipt，维护器依据负 utility、低利用、重复度、依赖破坏和漂移触发 rerank/merge/prune/demote。任何结构性 rewrite 都要能沿 lineage 回滚整个依赖闭包。

### 验收不变量

- candidate 验证过程中 kill registry；重启后它只能保持 candidate 或完整 admitted，不能出现可检索但无 AdmissionDecision/lineage 的半发布版本。
- 连续 Add 1,000 个近重复 Skill；检索质量、context 占用和选择误差达到预算前必须触发 maintenance，禁用 maintenance 的对照退化要进入 SLO。
- 一个 Skill 高频读取但 paired effect 不增反降；系统必须区分 usage 与 utility，并允许 demote/evict，不能以调用量自动晋级。
- 回滚父 Skill 时，依赖图中不兼容的组合 Skill 要同步隔离或固定到旧版本；不得留下悬空依赖。
- 每次库更新都能重建 `L_t -> L_t+1` 的 operator、输入版本、验证证据和责任主体；来源缺失的更新不得跨租户共享。

### 边界与风险

这是 taxonomy survey，不是一套端到端实现。124 篇材料的任务、模型、harness 与指标异构，作者明确反对把不同论文结果汇成统一排行榜；生命周期结构能指出必须做的决策，却不能证明哪种 verifier、存储拓扑或维护周期最优。OpenReview 页面本轮触发浏览器 challenge，接收信息依据 arXiv journal reference、comments 与论文首页复核。工程采用仍需按本项目风险和负载验证具体阈值。

## 4. Building AX evals that actually work

- 原始来源：[Microsoft for Developers 工程文章](https://developer.microsoft.com/blog/building-ax-evals-that-actually-work)
- 首次公开：2026-07-15；作者：Waldek Mastykarz（Microsoft Principal Developer Advocate）；类型：官方工程评测指南与平台案例；总分：**96/100**（来源可信度 24，问题具体性 20，架构深度 24，证据强度 14，Agent 服务端价值 14）

### 针对的问题

**来源事实/作者主张：** 很多 eval 会稳定地产生看似可信却无业务意义的分数：场景不代表真实用户，prompt 混入评分标准，criteria 只检查名称出现而不检查正确用法，LLM judge 与生成模型共享同一知识盲区，单次运行被当成信号，用户名、路径、OS 或 harness 更新又成为隐藏变量。结果是团队优化了分数，却没有改善 Agent 使用扩展/Skill 的实际效果。

### 原设计

**来源事实：** 文章要求 representative prompt、准确且无歧义的 criteria、每条件至少五次运行、clean environment 和 representative environment。prompt 必须只含用户任务，与 rubric 完全分离；每个原子检查定义 pass、fail、skip。judge 在真实 Agent 输出的人工金标上校准，并对同一输入重复测一致性；它只输出每项 verdict 与证据，版本比较和总分由确定性代码完成。语义版本比较等 judge 不可靠的任务改用专用工具。每次运行固定并记录 OS、工具、模型和 harness 版本；rubric 变更视为新测量仪器，未经重跑校准不得跨版本比较。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 创建 `EvalSpec` 注册表，分离 `scenario_prompt`、workspace fixture、condition（baseline/with-skill）、atomic checks、judge config 和 environment manifest。每项 check 输出 `PASS|FAIL|SKIP|ERROR`、evidence refs 与 judge version；score service 只做确定性聚合，并单独统计 skip/error，禁止 judge 心算总分。用 calibration suite 管理已人工判定的真实输出；Skill、model、harness、tool schema、rubric 或 workspace 类型任一变化都生成新的 comparison stratum。发布门比较 baseline 与 with-skill 的 lift、方差、成本和回归分布，不用一个全局平均数掩盖从零生成与存量集成差异。

### 验收不变量

- 把 rubric 文本意外拼进 Agent prompt；harness 必须在运行前检测 prompt/rubric hash 交叉污染并终止该样本。
- 同一输出连续 judge 产生不同 verdict；该 check 必须标记 uncalibrated，不能靠更换模型临时掩盖歧义。
- semver、算术或编译可由确定性工具判定时，judge 只能抽取证据；最终真假必须来自工具收据。
- OS、model、harness、Skill 或 rubric 版本未进入 manifest 的 run 不得与历史分数比较；自动更新不能静默改变测量条件。
- baseline 与 with-skill 各至少运行五次；3/5 对 2/5 这类弱差异不得宣称回归或提升，必须追加样本或标记不确定。

### 边界与风险

这是 Microsoft 的第一方开发者指南，不是同行评审 benchmark；“五次”是作者的实践起点，不是适合所有失败概率和发布风险的统计保证。案例聚焦 coding-agent extension，不能直接代表客服、支付或运维 Agent。LLM judge 即使经校准仍会漂移，人工金标也可能有错；高影响权限和真实业务效果应由确定性 verifier 或人工审批兜底。

## 5. How to test agent skills without hitting real APIs

- 原始来源：[Microsoft for Developers 工程文章](https://developer.microsoft.com/blog/how-to-test-agent-skills-without-hitting-real-apis/)；[Dev Proxy](https://devproxy.net)
- 首次公开：2026-07-17；作者：Waldek Mastykarz（Microsoft Principal Developer Advocate）；类型：官方工程文章、配置与完整样例；总分：**91/100**（来源可信度 24，问题具体性 20，架构深度 21，证据强度 13，Agent 服务端价值 13）

### 针对的问题

**来源事实/作者主张：** 一旦 Skill 调真实 API，50 个场景、3 个模型、5 次重复就至少产生 750 次调用；PATCH/DELETE 会污染在线状态，其他写入者又使结果不可复现。传统 mock server 需要重建分页、过滤和写语义并持续跟随真实 API 漂移；把 Skill 里的 URL 改成 localhost 还会改变模型看到的 token，因此测试的已不是将要发布的同一 Skill。

### 原设计

**来源事实：** Dev Proxy 在网络层拦截 Agent 对真实 base URL 的请求，以 JSON 配置定义 endpoint、seed data 和 `getAll/getOne/merge/delete` 等动作并在本地响应。Skill 继续使用生产 URL，不需要修改工件；每轮启动都重置数据。文章给出 product catalog 配置，并链接支持 GitHub Copilot CLI、Claude Code CLI 和 Codex CLI 的完整样例。作者强调目标不是完整复制后端，而是为 Skill 实际使用的操作提供稳定 URL、真实 payload 和正确 HTTP 语义。

### 对 Agent 服务器的采用设计

**本项目工程推断：** 在隔离 eval worker 的 egress 前放 `EvalHTTPProxy`。运行 manifest 将 skill hash、proxy rules hash、seed snapshot hash、API schema version 和 scenario ID 绑定；默认网络 deny，只允许规则中声明的 host/path/method。每个 repetition 从只读 seed 复制独立 state namespace，响应和状态转移写入 request/effect ledger。对分页、限流、超时、重试、409、部分失败和幂等键建立 fault profiles；未匹配请求必须 fail closed。评测结束比较 ledger 与预期 effect contract，而不仅是 Agent 最终文本。

### 验收不变量

- Skill 内保持完全相同的生产 URL 和 artifact hash；只改变代理开关，Agent context 不得出现 localhost 或测试提示。
- 重复运行含 PATCH/DELETE 的同一场景五次，每次初始 snapshot hash 与最终期望状态必须一致，run 间不可见彼此写入。
- 发出规则外 host/path/method 或代理失效时，worker 必须阻断外网并使样本失败，绝不能回落到真实 API。
- 在服务端已应用写入但客户端超时的 fault profile 下，Skill 重试必须携带幂等键或先对账；effect ledger 不得出现双写。
- API schema 更新后旧 proxy contract 必须显式失效；契约测试未通过前不能继续用旧仿真产生发布分数。

### 边界与风险

这是工程指南而非生产 benchmark。代理只对已建模的 endpoint 和语义逼真，可能漏掉鉴权、缓存、队列、异步回调、配额与跨服务事务；“每次 reset”也不自动清理代理外部的副作用。若 Skill 的价值依赖真实服务质量，还需要受控 staging/canary，而不能以仿真替代全部集成验证。代理本身是高权限中间人，配置、证书和录制 payload 必须按租户隔离并避免保存真实 secret。

## 综合采用结论

这五篇组合出的不是一个新总分，而是一条四层评测链：

1. **Meaningful scenario**：先定义代表真实用户与环境的任务、效果 contract 和 baseline。
2. **Useful skill**：通过 matched no-skill counterfactual 分离 reliance、signed utility、harm 与成本，不能用自报或调用量代替。
3. **Process fidelity**：用 selection/following/composition/reflection rubric 解释为何有用或为何失败，但所有正向 verdict 必须引用轨迹证据。
4. **Effect validity**：用隔离 API、真实 HTTP 语义、确定性工具和 effect receipt 证明动作真的发生且没有污染生产。

对应的 Skill 发布状态机应为：`draft -> candidate -> shadow -> admitted -> promoted`，任一阶段都允许 `quarantined/demoted/rolled_back`；每次转移绑定 artifact、rubric、environment、verifier 和 counterfactual 版本。这样“有用”才是一项可复验的发布声明，而不是 Skill 文档、Agent 叙事或单次演示的属性。
